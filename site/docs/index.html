GET STARTED

Install Zanskar

Zanskar 1.0 runs as a single instance: one gateway with an embedded SQLite database, plus a guacd sidecar if you want RDP or VNC desktops. Two supported install paths: the deb/rpm package on a Linux server, or the signed container image with Docker Compose. Both were exercised on a clean Ubuntu 24.04 machine before this release was cut.

1. Install from the package

Download the package for your architecture, the checksums and the signature bundle from the latest release. The commands below use amd64 and the .deb; swap arm64 or .rpm as needed.

V=1.0.0
B=https://github.com/albatroxxx/zanskar/releases/download/v$V
curl -LO $B/zanskar_${V}_linux_amd64.deb
curl -LO $B/SHA256SUMS
curl -LO $B/SHA256SUMS.sigstore.json

Verify integrity and origin. The signature is keyless Sigstore; the identity must be this repository's release workflow at this tag.

sha256sum -c SHA256SUMS --ignore-missing
cosign verify-blob --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp "^https://github.com/albatroxxx/zanskar/.github/workflows/release.yml@refs/tags/v$V\$" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com SHA256SUMS

Install. The package creates the zanskar service user, /var/lib/zanskar for the database and recordings, a hardened systemd unit, and an example environment file. It does not start the service, because there is no configuration yet.

sudo apt install ./zanskar_${V}_linux_amd64.deb      # Debian / Ubuntu
# sudo rpm -i zanskar_${V}_linux_amd64.rpm           # RHEL / Fedora / SUSE
zanskar version

Configure with zanskar init

zanskar init writes /etc/zanskar/env (mode 0600), generates the master key, and prints the exact next commands with your paths filled in. Interactively it asks for the listen address, TLS mode, data directory, guacd, MFA and logging. Non-interactively it takes flags, which suits cloud-init and Ansible.

sudo zanskar init                                   # interactive

# behind a TLS proxy (Caddy, nginx) on the same host:
sudo zanskar init -non-interactive -behind-proxy

# serving TLS itself, reachable on the network:
sudo zanskar init -non-interactive -listen 0.0.0.0:8443 \
  -tls-cert /etc/zanskar/tls/cert.pem -tls-key /etc/zanskar/tls/key.pem \
  -guacd 127.0.0.1:4822

Back up /etc/zanskar/env now. It holds ZANSKAR_MASTER_KEY, which seals every stored credential. It is never written to the database or to zanskar backup archives. Losing it makes every vaulted credential unrecoverable.

Apply migrations, create the first admin, start

Run the database commands as the service user so it owns the SQLite files it will write to. init prints this block for you.

sudo bash -c 'set -a; . /etc/zanskar/env; set +a; \
  runuser -u zanskar -- zanskar migrate && \
  ZANSKAR_ADMIN_PASSWORD=<choose-one> runuser -u zanskar -- zanskar admin create \
    --username admin --name "Your Name"'

sudo systemctl enable --now zanskar
curl -k https://localhost:8443/readyz        # {"status":"ready"}

Logs go to journald: journalctl -u zanskar -f. Then continue with first sign-in.

2. Install with Docker Compose

The single-node stack is the gateway on SQLite with a persistent volume, guacd for desktops, and Caddy terminating TLS in front. The gateway port is never published; only Caddy's 80 and 443 are. A one-shot zanskar-migrate service applies migrations before the gateway starts.

git clone --depth 1 --branch v1.0.0 https://github.com/albatroxxx/zanskar.git
cd zanskar
cp deploy/.env.example deploy/.env
# edit deploy/.env:
#   ZANSKAR_MASTER_KEY=      -> output of: openssl rand -base64 32
#   ZANSKAR_VERSION=1.0.0    -> optional; `latest` is the newest stable release
#   ZANSKAR_SITE_ADDRESS=    -> optional public hostname for Let's Encrypt

docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml exec -e ZANSKAR_ADMIN_PASSWORD=<choose-one> \
  zanskar /zanskar admin create --username admin --name "Your Name"

The image is ghcr.io/albatroxxx/zanskar, built for linux/amd64 and linux/arm64, running as a non-root user on a distroless base. Verify its signature the same way as the checksums:

cosign verify ghcr.io/albatroxxx/zanskar:1.0.0 \
  --certificate-identity-regexp '^https://github.com/albatroxxx/zanskar/.github/workflows/release.yml@refs/tags/v1.0.0$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Without a site address Caddy serves https://localhost/ with a self-signed certificate (a browser warning, fine for a trial). With ZANSKAR_SITE_ADDRESS set and ports 80/443 reachable from the internet, Caddy obtains a Let's Encrypt certificate automatically. Data lives in the zanskar_data volume.

3. First sign-in

  1. Open the gateway URL and sign in with the admin username and password you created.
  2. MFA is mandatory by default. Scan the QR code with an authenticator app and enter the code to enroll. If you refresh mid-enrollment the page resumes where you were.
  3. You land in the admin console. The how-to guide walks through credentials, targets, policies and the first session.

Lost the only admin's authenticator? On the gateway host: zanskar admin reset-mfa --username admin. The reset is audited and the next sign-in enrolls a new one.

Configuration reference

Zanskar is configured entirely through environment variables. The package reads /etc/zanskar/env; Compose reads deploy/.env. Restart after changes.

VariablePurpose
ZANSKAR_MASTER_KEYRequired. 32-byte base64 key that seals every stored secret. Generate with openssl rand -base64 32 or zanskar keygen.
ZANSKAR_LISTEN_ADDRListen address. Default 127.0.0.1:8443. Plain HTTP is refused on non-loopback addresses.
ZANSKAR_TLS_CERT, ZANSKAR_TLS_KEYServe TLS directly. HSTS is sent automatically.
ZANSKAR_TRUST_PROXY_TLS, ZANSKAR_TRUSTED_PROXIESBehind a reverse proxy: honour X-Forwarded-* from the listed CIDRs so the audit log records real client IPs.
ZANSKAR_DB_DRIVER, ZANSKAR_DB_DSNsqlite (default) or postgres with a connection string.
ZANSKAR_RECORDINGS_DIRWhere session recordings are written. S3 storage is configured with the ZANSKAR_RECORDINGS_S3_* variables described in docs/deploy.md.
ZANSKAR_GUACD_ADDRguacd host:port. Unset disables RDP and VNC.
ZANSKAR_DOCKER_PATHContainer CLI for database sessions. Defaults to docker on PATH; set an absolute path or podman.
ZANSKAR_REQUIRE_MFADefault true. Only set false for throwaway installs.
ZANSKAR_ISSUERName shown in authenticator apps. Default Zanskar.
ZANSKAR_SIEM_SYSLOG_ADDR, ZANSKAR_SIEM_WEBHOOK_URL, ZANSKAR_SIEM_WEBHOOK_SECRETStream the audit log to a SIEM over syslog/CEF or as signed JSON to a webhook.
ZANSKAR_LOG_FORMAT, ZANSKAR_LOG_LEVELjson or text; debug, info, warn, error.

The full reference with every variable is docs/deploy.md in the repository.

Update to a new version

Migrations are forward-only and run automatically when the service starts, so an update is install-and-restart. Take a backup first; it is one command and runs while the service is up.

# package path
sudo bash -c 'set -a; . /etc/zanskar/env; set +a; runuser -u zanskar -- zanskar backup --out /secure/zanskar-$(date +%F).tar.gz'
sudo apt install ./zanskar_<new-version>_linux_amd64.deb   # or rpm -U for RPM systems
sudo systemctl restart zanskar
zanskar version
# Compose path: set ZANSKAR_VERSION to the new release in deploy/.env, then
docker compose -f deploy/docker-compose.yml pull
docker compose -f deploy/docker-compose.yml up -d

Upgrades keep /var/lib/zanskar, /etc/zanskar/env and, on Compose, the zanskar_data volume. Read the release notes for anything version-specific. Live sessions get a grace period to close when the service restarts.

Restore from a backup

sudo systemctl stop zanskar
sudo bash -c 'set -a; . /etc/zanskar/env; set +a; runuser -u zanskar -- zanskar restore --in /secure/zanskar-2026-09-25.tar.gz --force'
sudo systemctl start zanskar

Restore refuses to overwrite an existing database without --force and warns when the archive was sealed under a different master key, because its stored credentials would be unreadable. Restore the original key first if you have it.

Remove Zanskar

Removing the package stops and disables the service and removes the binary and unit. It deliberately keeps the database, recordings, configuration and the zanskar user so a reinstall finds your data.

sudo apt remove zanskar        # or: sudo rpm -e zanskar

To purge everything, including every vaulted credential and every recording, run the following as well. This is irreversible; take a final zanskar backup first if there is any chance you will need the audit history.

sudo rm -rf /var/lib/zanskar /etc/zanskar
sudo userdel zanskar

Recordings and the audit log are compliance evidence. Check your retention obligations before purging them.

On Compose, docker compose -f deploy/docker-compose.yml down stops the stack and keeps the data volume; add -v to delete the volume as well.

Security

Keep ZANSKAR_REQUIRE_MFA=true. Terminate TLS at the gateway or on the same host. Never expose guacd (port 4822) beyond the gateway. Escrow the master key somewhere the database backup cannot reach. Ship the audit log to your SIEM and run zanskar audit verify on a schedule.

Releases are signed with Sigstore and every GitHub Action and base image is pinned by digest; the repository carries OpenSSF Scorecard and Best Practices badges and CodeQL runs on every change. Report vulnerabilities privately through GitHub private vulnerability reporting; the security policy commits to an acknowledgement within three business days.
