Zanskar v1.8.0

30 October 2026

Access policies, redesigned. A policy now says who it is for, any number of groups and users picked from searchable lists, and holds grants. Each grant picks a type of target first (host, database, application or autoscaling group), then the targets with a protocol each, or tags as Key and Value rows, then its own conditions: standing or approval, the target's credential or the person's own login, an authenticator, clipboard, file transfer, idle and maximum, days to keep recordings, and time windows. One policy can give a team standing SSH to staging and approval-only RDP to production. Where grants overlap, standing access wins over approval and each limit is the strictest. Live sessions are checked again whenever a policy or a group changes, and end when a fresh connect would be refused or when clipboard or file transfer would now be off. Deleting a group takes it out of its policies, which stay. The access portal offers as me where a grant signs a person in with their own login.

Zanskar v1.4.1

23 October 2026

A security patch. Nothing in the gateway's own code changed: this is 1.4.0 rebuilt with Go 1.27.3 in place of 1.27.2. Go 1.27.2 has a flaw in its crypto/x509 certificate checking that govulncheck finds reachable from Zanskar (Go advisory GO-2026-6809, tracked as CVE-2026-111943): a man-in-the-middle could lean on an intermediate certificate that should be distrusted. Because Zanskar verifies certificates when it talks to LDAPS directory servers, OIDC providers and upstream targets, anyone running 1.4.0 or the 1.5.0-rc.1 prerelease should move to 1.4.1.

Zanskar v1.4.0

13 October 2026

A security release. In October the whole gateway was read end to end, by tools and by six reviewers, and every finding was fixed: eight serious ones in the session path and at sign-in, thirty-three of medium weight, seventeen smaller ones, thirty-one bugs, and the dead code that let some of them hide. The release is built with Go 1.27.2, which closes three denial-of-service advisories the 1.3.0 image carries.

  • Sessions obey the policy that admitted them: a ticket issued for a desktop or PowerShell session could open an SSH shell on the same host; now every session endpoint checks the ticket's protocol, a ticket is redeemed only by the sign-in that asked for it, and an approval-gated policy no longer lends its settings to a session a standing policy admitted. A clipboard-off policy now stops the text itself, not just the first frame, and the browser clipboard reaches a desktop only when you press Ctrl+V in it, not on every window focus.
  • Taking access away ends live sessions: disabling or locking an account, changing its roles or groups, revoking its sign-ins, and deleting or narrowing a policy end the sessions that access allowed. Before, an open session ran until its idle timeout. The person sees the reason, and live shadowing of SSH and PowerShell sessions now shows the session (it showed nothing).
  • Sign-in hardened: no open redirect after single sign-on; wrong authenticator codes lock the account after five, like wrong passwords; a temporary lock no longer throws a signed-in user out; completing a sign-in issues a new session token; changing your password ends your other sessions; password hashing and sign-in floods are bounded; pre-created directory accounts can sign in; LDAP group mappings match by full DN; allowed email domains apply only to verified addresses (trust email for Entra ID); and ZANSKAR_PUBLIC_URL makes single sign-on work behind a TLS-terminating proxy.
  • Database sessions sealed: the client container's network reaches the relay and nothing else, the session user gets no pgbouncer console, at most twenty sessions run at once, a reaper clears containers a crash left behind, and no docker child inherits the gateway's secrets.
  • Audit anchors: the head of the log is signed at start and every hour, logged as a line to ship off the host, and zanskar audit verify checks the anchors and the id sequence, so deleting the newest events is noticed. A client disconnect can no longer cancel an audit write. Failed file transfers and lost recordings are audited; mismatches on autoscaling instances once, not every poll.
  • Targets and certificates: a probe never replaces a pinned RDP or WinRM certificate (a changed one waits for an administrator to accept it); loopback, link-local, the gateway's own and cloud metadata addresses are refused at save and at connect for every protocol; approval-gated access to an autoscaling group can be requested; an uploaded TLS certificate that cannot serve is kept and explained, not deleted.
  • Operations: init --force keeps a key file, restore as root keeps the service's ownership, key rotate-master writes the key only where the service reads it, offline commands refuse a database with migrations pending, environment values are never silently ignored, timestamps compare correctly on SQLite, zanskar healthcheck for the container image, health checks and digest pins in the compose stack, and a Helm upgrade stops the old gateway first.
  • The API and the console: every error carries its request_id; the same situation gets the same code; deleting an account with history answers 409 has_history cleanly; the sign-in page downloads only itself; dialogs keep the keyboard inside; the player and tab bars work from the keyboard; a deep link survives sign-in; a restart no longer signs you out; the ended-session dialog says why, on terminal and desktop alike.

Zanskar v1.3.0

6 October 2026

Administrators can now work from a command line inside the console. It runs Zanskar commands only, opens with a fresh authenticator code, and records every line in the audit log. Authenticator codes also become single-use.

  • The console command line: the terminal-window icon at the top right of every admin page, or Ctrl+`, opens it. Thirty-four commands cover sessions, users, targets, policies, access requests, events, logs, settings, autoscaling groups and a restart. It is not a shell: pipes, variables and anything unlisted are refused, nothing takes a secret, and host operations stay on the host. See the guide and ADR 0027.
  • Same permissions as the console: only administrators get it, and each command is the same API request a console page makes, through the same checks.
  • A code that was just proved: it opens with a code from your authenticator, again after 15 idle minutes, and five wrong codes close it for 15 minutes. Signing in without a code, as an identity-provider account or when MFA is not required, does not count.
  • Audited in words: every line is an event, shown on the Events page as ran “sessions --live” on the command line, with the API routes it called in the details.
  • Each authenticator code works once: a code that was accepted, at sign-in, enrolment or the command line, is refused for the rest of its window, so a code read over a shoulder or a screen share cannot be used again. A reused code is recorded as one on the Events page. Before, a code could be replayed for about a minute and a half.
  • Dependencies: the console's session player no longer pulls a serializer with published advisories; the vulnerable code was never in the built console.

Zanskar v1.2.2

4 October 2026, fixes on top of 1.2.1

Moving a target no longer looks like an attack, WinRM sessions on Windows autoscaling groups can fail over again, recordings waiting to upload to S3 cannot be swapped by another user on the machine, and the console reads in plain words throughout.

  • Moving a target starts its trust afresh: saving a new address clears the trusted host key and pinned certificates, so you probe and trust it again. Before, the old key stayed trusted and the next connection was refused as a host key mismatch, audited like an attack. The console warns before you save.
  • WinRM failover on autoscaling: when a Windows instance is lost, a WinRM session offers to move to another instance again.
  • Private recording spool: with S3 storage, the gateway refuses a spool folder it does not own or that others can write to, so a recording cannot be swapped before upload. The package service and the containers were never exposed.
  • Plain words: access requests read as sentences in Events, a deleted user is named as such, protocols read as SSH, RDP, VNC, WinRM and database, and dates read as dates.
  • Smaller fixes: the session file panel works from the keyboard, long database endpoints no longer break names, confirming an already-confirmed authenticator answers 409 instead of 500, and the chart's migration job has limits.
  • Tested more thoroughly: 80% of the gateway's own code is exercised by tests, including whole terminal, desktop, WinRM and database sessions; several of these fixes were found that way.

Upgrading from 1.2.1 to 1.2.2

Install the new package, or set ZANSKAR_VERSION=1.2.2, and restart. No migration runs and no setting needs to change. One behaviour change: saving a target with a different address clears its trusted host key and certificates; probe it and trust it again. Zanskar v1.2.1

1 October 2026, a security update to 1.2.0

Database connections are verified by default, the master key can live in a file of its own, and every release file now comes with a software bill of materials, signed build provenance and a build anyone can repeat.

  • Database TLS verified by default: a new database target checks the database's certificate and needs its CA bundle (for Amazon RDS, your region's bundle). Encrypted, not verified is still there as an explicit choice, with a warning on the target. Existing targets keep the setting they had.
  • The master key in its own file: ZANSKAR_MASTER_KEY_FILE keeps the key out of the environment file. The file must be readable by its owner only, and zanskar key rotate-master rewrites it in place.
  • Key rotation cannot strand the key: rotation used to re-encrypt the database before saving the new key, so a failed save could lose it. It now checks it can save first, and prints the key if the save still fails.
  • Release files you can check: an SPDX bill of materials beside each archive, SLSA level 3 build provenance for every file (check it with slsa-verifier), and builds that give the same bytes when you rebuild the tag.

Zanskar v1.2.0

30 September 2026, after two release candidates

What the 1.0 manual QA round asked for. An install that serves HTTPS out of the box, MySQL and MariaDB alongside PostgreSQL, keyless SSH through a certificate authority as the recommended Linux path, guided AWS enrolment, and a console that owns its runtime settings, recording storage and logs.

  • Install and TLS: zanskar init defaults to a gateway-managed certificate on 443 with plain HTTP redirected; a self-signed certificate at first start, the real one uploaded on the Settings page and served on the next connection. Existing installs keep their behaviour.
  • Databases: MySQL and MariaDB sessions through the gateway's own relay sidecar, a Databases page separate from Hosts, a database name and a TLS mode per target up to verify-full, and a credential slot that can be vaulted, user-supplied or empty.
  • Keyless SSH: the certificate authority is generated in the console, which prints the TrustedUserCAKeys commands for each target; one principal per session certificate, a key id naming the Zanskar user in the target's auth log, an allowlist of login users, and a two-phase rotation with a certificate login test per target.
  • AWS: the gateway detects its own principal; enrolment previews the trust policy with the real principal, a CLI script and a CloudFormation template that create the role, and tests the role before saving, naming the failing stage. Windows autoscaling groups serve RDP and WinRM sessions, each instance pinned to the certificate it first presented.
  • Access control: per-target protocol rules inside one policy, one open request per target with editable and extendable grants, retention per policy and per target.
  • Operations: Settings applied live with install-time values read-only, a restart-required banner with a drain, recording storage in an S3-compatible bucket configured and moved from the console, a Logs page, zanskar key status | rotate | rotate-master.
  • Onboarding and audit: a one-time password for new local users replaced at first sign-in, auditor accounts strictly review-only, recording and transcript download audited, targets retired rather than erased, names instead of ids everywhere.
  • Console: Events and Recordings inside the admin console below Logs (the audit portal is for auditor-only accounts), audit details that read Authenticator enrolled rather than an action code, and a logo that takes you back to the first page.

Zanskar v1.0.0

25 September 2026

The first stable release. Zanskar reached it after two release candidates: rc.1 caught a signing break in the release pipeline before anything was published, and rc.2 passed pipeline verification and a clean-machine install test on both documented paths.

  • Sessions: SSH and WinRM terminals, RDP and VNC desktops through guacd, PostgreSQL through a credential-isolating proxy sidecar, SFTP file transfer beside the terminal.
  • Access control: users, groups and three roles; local accounts with Argon2id and mandatory TOTP, or OIDC and LDAP/AD; tag-based policies with time windows, session limits and clipboard/file switches; host-key and certificate pinning with admin approval.
  • Just-in-time access: approval-required policies, time-boxed grants, an Approvals queue, automatic expiry, full audit trail.
  • Autoscaling: AWS Auto Scaling groups via a cross-account role and EC2 Instance Connect, with failover when an instance disappears.
  • Audit: recorded sessions with command-seek playback, live shadowing and terminate, hash-chained audit log with verify, SIEM export, recording retention.
  • Operations: zanskar init, hardened systemd unit in deb/rpm packages, Docker Compose stack with Caddy TLS, backup and restore.
  • Supply chain: every artifact checksummed and keyless-signed with Sigstore, multi-arch image on ghcr.io, pinned CI, OpenSSF Scorecard and Best Practices badges, CodeQL clean.

What comes next

Next, decided after 1.2: a restricted admin CLI in the console, opened from its top-right corner the way a firewall's is. It runs a fixed set of zanskar operations inside the gateway, never a system shell, and records every command in the audit log. It will ship with a reference of every command and how to use them.

Phase 4: the cross-pod control channel that unlocks high availability and makes the Helm chart a supported path, SAML and SCIM, WebAuthn, delegated and multi-step approvers, access reviews, and GCP and Azure scale sets. Follow the roadmap.
