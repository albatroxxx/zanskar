# Zanskar 2.0.0

Kubernetes clusters are targets. A policy grants a cluster, with the namespaces a person may
reach, and their `kubectl` works through the gateway as them: every request impersonated,
recorded and refused outside the grant with a sentence. Amazon EKS is reached through a role
the gateway assumes, with nothing stored. Two migrations. Built with Go 1.27.4.

A new major, because clusters are a new kind of target beside hosts, databases and
applications, and the gateway takes on a new trust to reach them. Nothing is removed: every
1.x API route, configuration file and Terraform resource keeps working, and a 1.20.1 gateway
upgrades in place.

## Posture

**The gateway becomes a principal every enrolled cluster trusts to impersonate.** It holds a
service-account token or a client certificate for each cluster, sealed as every secret is, or
for EKS a role it assumes with its own AWS identity and no stored secret. The RBAC the console
prints grants impersonation of users and of the Zanskar groups the policies name, by name, and
nothing else, so what a stolen credential could do is bounded by what the cluster's RBAC lets
those groups do. Every request a person makes carries their username and groups to the cluster's
own audit log, which no shared kubeconfig gives. Zanskar's own guard-rail runs before RBAC: a
request that names a namespace outside the grant, a cluster-wide request without `cluster scope`,
or `port-forward` without its switch, never reaches the cluster ([ADR 0045](../adr/0045-kubernetes-clusters-as-targets.md),
[ADR 0048](../adr/0048-fabric.md)).

## Added

- **Kubernetes** in the admin sidebar: one tile per platform (Vanilla, EKS, GKE, AKS), each a tab
  counting its clusters. A cluster is a target whose API server's URL makes it one, with its CA
  bundle, its platform and whether sessions act as the person (the default) or as the credential
  (a shared identity, which the console and the audit say).
- **Two credential types for a cluster**, `kube_token` (a service account's token) and
  `kube_client_cert` (a certificate and its key, one PEM text), always vaulted; **Test** on the
  cluster reports its version, whether Zanskar may impersonate users and groups, and the
  namespaces it could list; **RBAC manifest** prints what to apply, naming the groups whose
  policies grant the cluster.
- **Kubernetes grants** in a policy: the clusters or tags, the **namespaces** the grant reaches
  (empty is every namespace), **cluster scope** and **port-forward**, both off by default. Where
  grants overlap, the scope is their union, while the clipboard and file switches stay the
  strictest. A change to a person's scope or groups ends their running cluster sessions.
- **Kubeconfig** under the Clusters tab of the portal starts a session at once and hands the
  person, once, a kubeconfig whose server is the gateway and whose token is the session's,
  embedding the gateway's certificate when it is self-signed. `kubectl` then works: lists,
  watches, `logs -f`, `exec` and `attach` over WebSocket, Table output, `auth whoami` and
  `auth can-i`. A request outside the grant is a `Forbidden` whose message names what the access
  covers. The session ends after the policy's idle time without a request (eight hours when the
  policy sets none), at its maximum, on terminate, on a policy change, or when the cluster's
  endpoint, CA, platform, identity mode or credential is edited; the token is refused the moment
  it ends. The recording is one line per request, discovery left out; a stream is a line when it
  opens and one when it ends, with its bytes.
- **Amazon EKS through a role**: the credential type `kube_eks` names the region, the role and
  the cluster, and the gateway mints the ExternalId; its **Setup** prints the trust policy (with
  the gateway's principal), the permissions policy and the access-entry or `aws-auth` mapping to
  the user `zanskar`; **Test** assumes the role and describes the cluster, naming the stage that
  failed. On **Add cluster**, choosing the role and **Describe** fills the API server and CA from
  AWS. The token the cluster accepts is the one `aws-iam-authenticator` defines, minted per
  session and reused for twelve of the fifteen minutes it lives, never stored. An EKS cluster's
  slot takes an EKS role and nothing else.
- **The configuration file and the Terraform provider** carry a cluster's fields and a grant's
  scope; the console command line's `target show` and `policy show` say them.
- **Audit**: `session.start` with protocol `kube`, the namespaces, cluster scope, port-forward and
  `acts_as`; `credential.test` for an EKS role's test.

## Changed

- A cluster that refuses the gateway's own credential (a token rotated away, a role no longer
  mapped) is told to the person as the gateway's fault, a `502` with a sentence, rather than the
  API's `401` that read as their kubeconfig being wrong.

## Fixed while building it

- The policy API's write body lacked the grant scope the model validated and stored, so the
  editor never sent it (2.0.0 is the first release with the fields; nothing shipped was affected).
- The configuration file and the Terraform provider had their own copy of the target and grant
  shapes without the Kubernetes fields: an export then import would have widened a grant to every
  namespace and turned a shared identity into impersonation, and a Terraform update would have
  turned a cluster into a host. Both carry the fields now, and their tests read the receiving
  gateway's own answer rather than comparing two exports.
- Run against a real cluster (kind, Kubernetes v1.37.0): the cluster test asked whether it may
  impersonate groups without naming one, which RBAC answers "no" for a grant by `resourceNames`,
  so it reported `impersonate_groups: false` while impersonation worked; and `kubectl auth whoami`
  and `auth can-i` were refused as cluster-wide requests. Both fixed before release.

## Upgrading from 1.20.1

Back up first: migrations 0056 and 0057 add columns and rebuild three tables on SQLite. Install
the new package, or set `ZANSKAR_VERSION=2.0.0`, and restart. Cluster sessions need
`ZANSKAR_PUBLIC_URL` set to the gateway's `https://` address, since the kubeconfig names it;
without it the Kubeconfig button says so and nothing else changes. Nothing changes for anyone
until a cluster is enrolled.
