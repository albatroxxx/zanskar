# Zanskar 1.2.0-rc.2

**Release candidate for the 1.2.0 staging test.** Not for production: `latest` does not move, and the container image is tagged `1.2.0-rc.2` only. The notes below are the 1.2.0 notes.

**What changed since rc.1**, all of it found by testing rc.1 on a staging gateway with a real Active Directory domain, a domain-joined Windows host, an RDS database and two autoscaling groups:

- Saving an access policy from the console failed outright, on every policy. The API rejected the two fields the form has been sending since 1.2.0 gained per-target rules and retention. This was the release blocker and is why rc.1 must not become 1.2.0.
- Windows autoscaling groups could be enrolled and would report healthy instances, and then refuse every session. They work now, with each instance pinned to the certificates it first presented (ADR 0024).
- A WinRM credential that authenticates and is then refused a shell said nothing useful. It now names the cause: Zanskar opens a WinRS shell, which Windows grants to local administrators only.
- Six console fixes from the same pass: alignment inside dialogs, the portal's opening tab, the database button's colour, a terminal that kept counting after its session ended, seconds on log and audit times, and engine names that disagreed between a table and its drawer.
- Installation points at the newest release rather than a pinned version, and documents `go install …/cmd/zanskar@latest`.
- The guide gained the Active Directory walkthrough it never had, and the autoscaling section is rewritten for Windows.

The second release of Zanskar, an **agentless access gateway** for the machines and managed
databases you already run: SSH, RDP, VNC and WinRM sessions in the browser, brokered
PostgreSQL, MySQL and MariaDB sessions, vaulted credentials, access policies, just-in-time
approvals, session recording and a tamper-evident audit log. One Go binary with the web UI
embedded, nothing installed on the targets.

1.2.0 is what the 1.0 manual QA round asked for: an install that serves HTTPS out of the box,
MySQL and MariaDB alongside PostgreSQL, keyless SSH through a certificate authority as the
recommended Linux path, guided AWS enrolment, a console that owns its runtime settings,
recording storage and logs, and onboarding that hands new users a one-time password. It
remains a **single-instance** release: one gateway, embedded SQLite or PostgreSQL, and a
`guacd` sidecar for RDP and VNC.

## Highlights

**Install and TLS**
- The installation instructions point at the **newest** release rather than a pinned version:
  the package commands resolve it from the releases redirect, the container image tag defaults
  to `latest`, and `go install github.com/albatroxxx/zanskar/cmd/zanskar@latest` is documented
  as the one-line path, with its caveats (no web console, no version string).
- **HTTPS out of the box.** `zanskar init` now defaults to a gateway-managed certificate on
  `0.0.0.0:443` with plain HTTP on port 80 redirected (`ZANSKAR_TLS_MODE=managed`,
  `ZANSKAR_HTTP_REDIRECT_ADDR=:80`). A self-signed certificate is generated at first start;
  upload the real one on the Settings page and it serves on the next connection, no restart.
  `zanskar init -behind-proxy` keeps the loopback-behind-a-proxy shape. Existing installs
  keep their behaviour: the mode is derived from the variables they already set.
- The packaged unit grants `CAP_NET_BIND_SERVICE` so the unprivileged service can bind 443
  and 80.

**Databases**
- **MySQL and MariaDB** sessions, including Amazon RDS, through the gateway's own relay
  sidecar (`zanskar dbproxy`, the gateway image run beside each session). As with
  PostgreSQL, the user's client container never holds the database password.
- A **Databases** page separate from Hosts, kind-first forms, a database name and a TLS mode
  per target (`disable`, `prefer`, `require`, `verify-full` with an optional CA bundle),
  honoured by both sidecars.
- A tri-state credential slot: vaulted, user-supplied at connect time, or none.

**SSH without stored keys**
- **The certificate authority is the recommended way to reach Linux targets.** Creating an
  `ssh_ca` credential generates the authority; the console prints the exact
  `TrustedUserCAKeys` commands for each target. Every session gets a certificate for one
  login user, valid for minutes, with a key id that names the Zanskar user in the target's
  auth log. A per-authority allowlist limits the login users it will issue for.
- **Two-phase rotation** of the authority key: prepare the next key, install both public
  keys, test each bound target with a real certificate login, cut over, retire. No session
  breaks on a host that has not learned the new key.

**Autoscaling groups on AWS**
- **The gateway knows its own principal**: detected from its instance profile or IRSA and
  shown on the Autoscaling page. Enrolment previews the IAM documents before the group is
  saved: a trust policy with the real principal (never a placeholder), the permissions
  policy, an AWS CLI script and a CloudFormation template that create the role.
- **Test access** assumes the role with the ExternalId and describes the group before
  saving, and names the failing stage: trust policy, permissions, or no such group.
- **Windows autoscaling groups now serve sessions** (ADR 0024). A group could already be
  enrolled with RDP and WinRM capabilities and would sync and report healthy instances, but
  every connection was refused. Each instance is now pinned to the RDP and WinRM certificate
  it first presented; a certificate that changes under us marks that instance unhealthy and is
  audited, rather than being trusted quietly. Windows instances are expected to come from an
  image that already carries the HTTPS WinRM listener, since nothing configures a machine that
  may be gone within the hour.
- A WinRM credential that authenticates and is then refused a shell now gets a plain answer:
  Zanskar opens a WinRS shell, which WinRM grants to local administrators only, so membership
  of *Remote Management Users* is not enough. It used to be an opaque 409.

**Access control**
- Per-target protocol rules inside one policy.
- Just-in-time access: one open request per target, editable grant duration, extensions of
  an active grant, a nav badge and expiry notices.
- Recording retention per policy and per target, fixed on each recording when its session
  starts; the sweeper honours it.

**Operations from the console**
- **Settings**: typed runtime settings applied live (login banner, MFA requirement, guacd
  address, log level, relay image) with their source shown; install-time settings listed
  read-only.
- **Restart required** banner when the environment file changed since start (variable names
  only), and a restart with a drain of live sessions.
- **Recording storage**: an S3-compatible bucket configured, probed and switched from the
  console, with an audited move of existing local recordings.
- **Logs**: the gateway's recent log lines from an in-memory ring, filtered and downloadable,
  without shell access.
- `zanskar key status`, `zanskar key rotate` and `zanskar key rotate-master` for the key
  ring and the master key.

**Onboarding and identity**
- Creating a local user without a password generates a one-time password shown once; the
  user replaces it at first sign-in, before the second factor.
- Auditor-only accounts are review-only and cannot reach targets.

**Audit and recordings**
- Download recordings and command transcripts, each download audited.
- Targets and autoscaling groups are retired, not erased, so session history keeps its names;
  deletion is refused while a policy or a live session still references them.
- Names instead of ids throughout the audit log and session lists.

**Console**
- Modal action rows stay put, credential bindings apply on Save, a key-file picker for SSH
  keys, recording player transport controls, clipboard sync with RDP and VNC, a pulsing
  recording indicator.

**Console**
- Six things the manual QA pass found: rows inside a dialog no longer inherit the closing row's
  right alignment (and a textarea outside a field wrapper no longer renders 170px wide); the
  user portal opens on a tab that has something in it; the database chip is no longer the same
  colour as a warning; a terminal whose session has ended stops its counters, drops the
  Recording dot and says why it ended; log and audit times show seconds; and the database
  drawer writes engine names the way the table beside it does.

## Security posture

OpenSSF Scorecard and Best Practices (passing) badges, CodeQL, gosec, govulncheck, gitleaks,
Trivy and Go native fuzz targets on every change; local git hooks for secrets and
vulnerabilities; all GitHub Actions and base images pinned by digest; branch protection on
`main` with eight required checks; private vulnerability reporting enabled. Threat model:
`docs/threat-model.md`. Report vulnerabilities privately:
<https://github.com/albatroxxx/zanskar/security/advisories/new>.

## Known limitations

- Single instance only; running more than one replica breaks cross-pod admin terminate and
  auditor shadowing (Phase 4).
- The MySQL and MariaDB relay was verified with unit tests, the Go MySQL client, and
  sessions through the actual `mysql:8`, `mariadb:11` and `postgres:16` client containers on
  the 1.2.0 staging gateway. Report anything a particular client version does differently.
- Autoscaling instances are pinned on **first sight**, without an administrator approving a
  fingerprint, because the instance did not exist a minute ago (ADR 0024). For SSH the host key
  is cross-checked against the serial console where AWS publishes it; for the Windows
  certificates there is no such cross-check.
- No SAML, SCIM or WebAuthn yet (Phase 4). Passwords for Windows and database targets are not
  rotated by Zanskar; the systems that own those accounts do that better.

## Upgrading from 1.0.0

Install the new package or set `ZANSKAR_VERSION=1.2.0` and restart. Migrations 0017 to 0023
run at start (new columns and tables; no data is rewritten), plus 0024, which adds the two
per-instance certificate columns for Windows autoscaling groups. An existing install keeps its TLS
behaviour: with `ZANSKAR_TLS_CERT` set the mode is `file`, otherwise `proxy`, exactly as
before; only a fresh `zanskar init` defaults to managed TLS on 443. The MySQL and MariaDB
relay image defaults to `ghcr.io/albatroxxx/zanskar:1.2.0` and can be pointed at a mirror on
the Settings page. `ZANSKAR_AWS_GATEWAY_PRINCIPAL` can be removed on EC2 and EKS gateways,
which now detect it.
