# Zanskar 3.0.0

Cloud accounts are targets, and approvers are a role. A policy grants a role in an AWS account
the way it grants a host; the person opens the AWS console or takes command-line credentials
through the gateway, for a session of known length, with what they did read back from CloudTrail
into the recording. An approval grant names who decides it, and those people get a portal of
their own. One migration. Built with Go 1.27.4.

A new major, because a cloud account is a new kind of target and the trust the gateway takes to
reach it is the widest it has taken, and because the roles go from three to four. Nothing is
removed: every 2.x API route, configuration file and Terraform resource keeps working, and a
2.0.0 gateway upgrades in place.

## Posture

**The gateway becomes a principal that can act inside enrolled AWS accounts with the enrolled
roles' permissions, on a person's behalf.** It is bounded as autoscaling groups and EKS clusters
bound theirs: each role's trust policy names this gateway's principal and an ExternalId Zanskar
minted, so no other principal can use the enrolment; enrolment is an administrator's audited act;
the gateway holds no long-lived secret for any account; every credential it mints carries the
person's username as `SourceIdentity` and a session name that is Zanskar's session id, so
CloudTrail in the account names the person and the session. A console session, once issued,
runs to its end: AWS gives no way to cut it short without IAM writes on the role, and the console
says the two end times when an administrator terminates such a session
([ADR 0050](../adr/0050-cloud-accounts-as-targets.md)).

**A fourth role, `approver`, and a designation on the grant.** Where an approval grant names
approvers, they alone approve and deny its requests; an administrator sees the request, revokes
the grant, and does not decide unless named. Nobody decides their own request. The role grants
nothing else: an account holding only `approver` reaches no target and reads no recording
([ADR 0049](../adr/0049-approvers.md)).

## Added

- **Approvers.** A fourth role beside admin, auditor and user, ticked on the user form or granted
  by a provider's **Approver groups** (OIDC claim values, LDAP groups), withdrawn when the person
  leaves them. An approval grant names up to 32 **approvers**, groups or people; a request whose
  named approvers are nobody but the requester is refused when made. Each named approver with
  an address is mailed on their own, with a link into the **Approvals** portal: the requests
  waiting for them, the grants they may revoke, and what they decided. The admin queue shows
  each request's approvers and offers Approve and Deny only where the reader may decide.
- **Cancel and End for the requester.** A pending request can be cancelled, and an approved
  grant ended early, by the person who asked; each is its own audit event and ends the sessions
  as a revoke does.
- **Cloud accounts** in the admin sidebar. A target is one role in one AWS account: the account,
  an alias, the role's ARN, how long a session may run (15 to 720 minutes, 60 by default) and the
  region the console opens in. **Setup** prints the trust policy with the gateway's principal and
  the minted ExternalId, the activity policy (`cloudtrail:LookupEvents`), the CLI and the
  CloudFormation that put both on the role. **Test** assumes the role for the target's minutes,
  names the stage that refused (the trust policy, the duration, the gateway's own identity when
  it is itself an assumed role), and says whether the activity can be read.
- **Cloud grants** in a policy, with two switches, **Console** and **Command line**, both on by
  default and the strictest across overlapping grants. A cloud session has no idle timeout; its
  length is the grant's maximum, capped by the role's.
- **The portal's Cloud tab.** **Open console** starts a session and posts a sign-in into a new
  tab; **Command line** shows a `~/.aws/config` stanza whose `credential_process` fetches
  fifteen-minute credentials from the gateway with a bearer the session owns, re-minted while
  the session lives. A terminate stops the command line within fifteen minutes.
- **Activity from CloudTrail.** During a live cloud session, **Activity** on the Sessions page
  reads what the person did and appends it to the recording, one line per event (time, service
  and call, read-only or write, the resources); fifteen minutes after the session ends the
  gateway reads once more, then finishes the recording. Events arrive up to fifteen minutes
  late; the recording says so.
- **On the record.** `session.start` with protocol `cloud`, `session.cloud.credentials` for each
  fresh mint, `session.cloud.console` for each sign-in (never the token), `session.cloud.activity`
  for each read, `target.cloud.test`, `access.request.cancel`; a `user.roles.update` naming the
  provider when approver groups grant or withdraw the role.
- **The configuration file, the Terraform provider and the console command line** carry a
  grant's approvers, a cloud role's fields and a cloud grant's switches; `requests --mine` lists
  an approver's queue.

## Changed

- The Approvals route tree admits administrators as well as approvers, so a mail link works for
  an administrator a grant names.
- The console's Content-Security-Policy lets the sign-in form reach AWS's sign-in and console
  hosts, and no other host; the API's policy is unchanged.
- An account a provider leaves with no role, because its approver group was its only role,
  becomes a plain user rather than one with no portal.

## Fixed while building it

Two reviews went through the batch before release; every finding was fixed with a test.

- An administrator a grant named as approver had no button to decide with: the queue hid Approve
  and Deny on every named request, and the portal bounced administrators. The gateway now says,
  per request, whether its reader may decide, and both views read that.
- A disabled account counted as a decider and was mailed; it counts for nothing now.
- The policy API's write body lacked the cloud grant's switches, so the editor's cloud grants
  would have been refused as malformed (first release with the fields; nothing shipped was
  affected).
- A console sign-in issued in the moment a session was being terminated was handed out and never
  recorded; it is discarded now.
- A failed federation call wrapped the request URL, which carries the credentials, into its
  error; it names the dial error alone.
- A GovCloud or China role could be enrolled and would have been sent to the commercial sign-in
  endpoint; the `aws` partition alone is accepted until the others have their endpoints.
- A region edit ended a role's live sessions through the address it derives; it keeps them.
- A hand-written cloud role in the configuration file planned an update on every import.

- `internal/access/approvers.go` (who decides, re-resolved at list and decision time),
  `internal/notify/direct.go` (one mail per approver), `internal/cloud/sts.go` (the per-session
  mint with `SourceIdentity` and tags, the federation exchange), `internal/cloud/cloudtrail.go`

  (a session without a socket: the credentials and console routes, the final read),
  `internal/target/cloud.go` (validation, Setup, Test), `internal/recording/append.go` (a
  finished recording gains a line when the gateway did not come back).
- Migration 0058, both engines: the approver role and the `cancelled` status in their CHECKs, the
  protocol `cloud` in three, seven cloud columns on targets; SQLite rebuilds four tables.
- One new module, `github.com/aws/aws-sdk-go-v2/service/cloudtrail` (Apache-2.0); `golang.org/x/crypto`
  to 0.59.0; notices regenerated.
- The Helm chart is 2.0.0 for application 3.0.0, keeping the offset it has had since 0.x.
- Verified with fakes and a built gateway: `go test -race` on SQLite and Postgres, the console
  suite (121 files, 888 tests), the Terraform acceptance suite against a running gateway. **Not
  run against a real AWS account**: Setup, Test, a session, the console sign-in and the CloudTrail
  read have met fakes only, and Open console has not been pressed in a real browser since the
  policy change. The owner tests those by hand first.

## Upgrading from 2.0.0

Back up first: migration 0058 adds columns and rebuilds four tables on SQLite. Install the new
package, or set `ZANSKAR_VERSION=3.0.0`, and restart. Cloud sessions need `ZANSKAR_PUBLIC_URL`
set to the gateway's `https://` address, as cluster sessions do; without it the Cloud tab's
buttons say so and nothing else changes. A reverse proxy that replaces the gateway's
`Content-Security-Policy` header leaves Open console with a blank tab: pass the gateway's header
through. Nothing changes for anyone until an approver is named or a cloud role is enrolled; a
provider's approver group that was an account's only role now leaves it `user` when the person
leaves the group.
