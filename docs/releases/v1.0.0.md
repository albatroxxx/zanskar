# Zanskar 1.0.0

The first stable release of Zanskar, an **agentless access gateway** for the machines you
already run: SSH, RDP, VNC and WinRM sessions in the browser, plus brokered access to managed
databases, with vaulted credentials, access policies, just-in-time approvals, session
recording and a tamper-evident audit log. One Go binary with the web UI embedded, nothing
installed on the targets.

1.0 is a **single-instance** release: one gateway, embedded SQLite, and a `guacd` sidecar
for RDP and VNC. Multi-replica HA and the Helm chart are preview-only until Phase 4 lands.

## Highlights

**Sessions**
- SSH terminal in the browser over WebSocket, with SFTP upload/download in a side panel
  when the policy allows file transfer.
- RDP and VNC desktops through `guacd`, with clipboard policy and a files panel.
- Windows command line over WinRM, TLS-pinned to the host's listener certificate.
- Managed/PaaS database access (PostgreSQL first) through a per-session client container
  that talks to a credential-holding proxy sidecar: the user never sees the database
  credential, not even from a shell escape.
- Every session is recorded (asciicast for terminals, Guacamole-format for desktops), admins can
  watch live, terminate, or replay with command markers; auditors can shadow.

**Access control**
- Users, groups and roles (admin, auditor, user); local accounts with Argon2id passwords and
  mandatory TOTP, or OIDC and LDAP/Active Directory sign-in with audited group-to-role
  mapping.
- Access policies bind subjects to targets with protocol, time window, idle and maximum
  session limits, clipboard and file-transfer switches.
- **Just-in-time access (PIM):** policies can require approval; users request time-bound
  access with a reason, admins approve, deny or revoke, grants expire automatically and every
  step is audited.
- Host-key and certificate pinning: trust on first use at enrollment, admin approval, any
  later change blocks connections until re-approved.

**Credentials and secrets**
- Vaulted passwords, SSH keys and an SSH certificate-authority mode; envelope encryption
  (AES-256-GCM data keys wrapped by a master key) with key versioning and rotation.
- The master key is never written to the database or included in backups.

**Autoscaling groups**
- AWS Auto Scaling groups enrolled through a cross-account IAM role: healthy-pool tracking,
  EC2 Instance Connect credentials, and a failover prompt when the active instance goes away.

**Audit and compliance**
- Append-only, hash-chained audit log with `zanskar audit verify`; SIEM export.
- Recording retention by age and size with an audited hourly sweep.
- `zanskar backup` / `zanskar restore` for the SQLite database and recordings.

**Operations**
- `zanskar init` writes the configuration interactively or from flags; a hardened systemd
  unit ships in the deb/rpm packages.
- Docker Compose single-node stack with Caddy TLS pulls the signed multi-arch image from
  `ghcr.io/albatroxxx/zanskar`.
- Every release artifact is checksummed and signed with Sigstore (keyless, GitHub Actions
  identity); the verify commands are below.

## Security posture

OpenSSF Scorecard and Best Practices (passing) badges, CodeQL, gosec, govulncheck, gitleaks and
Trivy on every change, all GitHub Actions and base images pinned by digest, branch protection
on `main`, private vulnerability reporting enabled. Threat model: `docs/threat-model.md`.
Report vulnerabilities privately: <https://github.com/albatroxxx/zanskar/security/advisories/new>.

## Known limitations

- Single instance only; running more than one replica breaks cross-pod admin terminate and
  auditor shadowing (Phase 4).
- Database access supports PostgreSQL; MySQL via ProxySQL is next.
- No SAML, SCIM, WebAuthn or credential auto-rotation yet (Phase 4).

## Upgrading from a release candidate

`1.0.0-rc.1` and `1.0.0-rc.2` share the schema with 1.0.0. Install the new package or set
`ZANSKAR_VERSION=1.0.0` and restart; migrations are a no-op.
