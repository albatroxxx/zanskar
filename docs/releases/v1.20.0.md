# Zanskar 1.20.0

Security keys and passkeys as a second factor (ADR 0028). A YubiKey, or the passkey in a phone,
laptop or password manager, works wherever an authenticator code is asked: at sign-in, for every
action that asks for a recent code, and to open the console command line. Unlike a code, a key
cannot be phished: it signs for the address the browser is really on, so a look-alike site gets
nothing the gateway accepts. People add keys under their username in the sidebar; a first sign-in
can take a key instead of the app. A new setting, *Administrators must use a security key*, has an
administrator who has a key answer with it. Nothing widens what a session can reach. One migration
(0055). Built with Go 1.27.4.

## Posture

- **Keys need the public address.** A key is registered to the host name in `ZANSKAR_PUBLIC_URL`.
  With none set, or an IP address there, keys are off: *Use your key* is greyed out with the
  reason, the gateway logs `security keys are off` at start, and codes work as before. Changing
  the host name later means everyone registers their keys again.
- **Nothing is required of anyone.** Keys are offered, not demanded; *Administrators must use a
  security key* is off until an administrator turns it on.

## Added

- **Use your key** beside every code field: the sign-in's second step, the settings that decide
  where a credential goes, approving access, making an API token, host actions and updates, and
  the command line. It shows only for an account with a key. A key that is refused counts against
  the same limits as a wrong code, and a key whose signature counter went back is refused and
  audited as a possible copy.
- **Security keys in the account dialog** (the username in the sidebar): each key with when it was
  added or last used and whether it is a synced passkey, *Add key*, *Rename*, *Remove* and *New
  recovery codes*, up to ten keys. Adding a key beside a second factor, adding the app beside keys,
  removing a key and new codes ask for a fresh code or key first; a first key asks for the password
  again. Adding a key signs the account's other sessions out, as adding an app does.
- **A key as the first second factor**: the first sign-in offers *Use a security key instead* of
  the authenticator app. Recovery codes come with the first second factor of either kind, shown
  once, and stay when another is added.
- **Administrators must use a security key** (Settings, *Sign-in*; off by default, and changing it
  asks for a recent code): an administrator who has a key no longer passes with the app's code;
  recovery codes still work, and an administrator without a key is asked to add one.
- **Keys for accounts a provider signs in**: they may add keys for the prompts that ask Zanskar's
  own second factor (step-ups, the command line); sign-in asks for one only when the provider has
  *Also ask for a Zanskar authenticator* on.

## Changed

- **Has a second factor** means an app or a key everywhere: the *Require an authenticator* gate, a
  grant's *Authenticator* condition, the command line, the *No authenticator yet* tile, and
  providers that ask for a Zanskar factor. *Reset authenticator* (console or `zanskar admin
  reset-mfa`) removes the app, every key and every recovery code.
- **Audit**: keys added, renamed and removed (`user.key.*`), recovery codes replaced
  (`user.mfa.recovery_codes`), and every second-factor check with its method; sign-ins read
  *signed in with a security key* or *with a recovery code*.

## Fixed while building it

- A sign-in that still owed the key of an account with keys and no app could have enrolled an app
  with the password alone and passed with it; app enrolment now refuses a sign-in that owes the
  factor the account has.
- A password an administrator reset on such an account could have chosen the next password from
  the session that still owed the key; the password change now counts keys as a second factor.
- Beside keys, a session with only the password could have added an app and, with the proof its
  confirmation writes, removed the owner's keys; adding an app beside keys now asks for a fresh
  proof at both steps.

## For contributors

- `internal/auth/webauthn.go` (`Keys`: store and ceremonies over go-webauthn v0.18.2),
  `factors.go` (`Factors`: the app and keys together, the one place any "has a second factor" or
  "check a code" question goes), `keys_handlers.go` (the routes). Tests use a software
  authenticator with real ES256 signatures (`softkey_test.go`).
- Migration 0055 (`webauthn_credentials`), both engines; keys are plain rows (ADR 0047).
- Nine new modules from go-webauthn's tree (CBOR, COSE, TPM and JWT parsing), all MIT, BSD or
  Apache-2.0; third-party notices regenerated.

## Upgrading from 1.19.3

Back up first: migration 0055 adds a table. Install the new package, or set
`ZANSKAR_VERSION=1.20.0`, and restart. Keys work once `ZANSKAR_PUBLIC_URL` names the host people
use, behind a certificate browsers trust; the journal says `security keys are off` and why if not.
Nothing changes for anyone until they add a key.
