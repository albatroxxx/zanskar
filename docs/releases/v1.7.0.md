# Zanskar 1.7.0

Applications change shape. The identity-aware proxy of 1.5 and 1.6, with its apps domain,
wildcard certificate and client trust, is gone; an application now opens in a browser that
runs beside the gateway, in a container made for that session, streamed to the person as
pixels through guacd the way a VNC desktop is ([ADR 0034](../adr/0034-applications-isolated-browser.md),
superseding ADR 0033). Enrol an application with its address and a policy, and it opens.
Read **Upgrading from 1.6.0** below: migration 0032 drops what the proxy needed, and the
gateway host needs a container runtime for applications, as it does for databases. Built
with Go 1.27.3.

## Highlights

**Applications open in an isolated browser**
- An application is a target with an upstream, `http://host[:port]` or `https://...`,
  granted by policies under `http`. No apps domain, no certificate, no DNS record, nothing
  installed on the client. The Applications page lists what the gateway host still needs
  (guacd, a container runtime, the browser image) until all three are in place.
- Per session the gateway starts an internal network with no route out, a browser
  container on that network alone, and a relay container on it and the host's bridge. The
  relay forwards the upstream's one port to the address the gateway resolved under the
  address rules, and hands the browser's screen to guacd once, with a password made for the
  session. The browser's resolver maps the upstream's name to the relay and everything else
  to nothing.
- The browser is Debian's Chromium in kiosk mode, published as
  `ghcr.io/albatroxxx/zanskar-browser`, signed and scanned like the gateway's image. It runs
  as an unprivileged user with Chromium's own sandbox on, under a seccomp profile that is
  Docker's default plus the namespace and chroot calls the sandbox needs; the container is
  read-only, without capabilities, with pid, memory and cpu limits. Chromium policy allows
  the upstream's origin only and blocks downloads, printing, developer tools, extensions,
  sign-in, sync, password saving, autofill, safe browsing and metrics. Nothing of the
  session outlives the container; a reaper removes what a crash leaves.
- The session is a desktop session: on the Sessions pages, terminable, shadowable, recorded
  as a pixel stream and replayable, with the policy's idle and maximum limits and its
  clipboard rule. `ZANSKAR_APPS_MAX_SESSIONS` (default 10) caps open application sessions,
  since each is a Chromium.
- An https upstream is verified by the browser against the system roots or the bundle
  pasted on the target, never switched off.

**Settings**
- `apps.browser_image` names the browser image (`ZANSKAR_BROWSER_IMAGE` in the environment
  file); from the console only a digest-pinned reference, behind a fresh authenticator code,
  like the relay image. `database.proxy_image` is titled *Relay image*: the gateway's own
  image, run beside each MySQL session and each application session.

**Removed**
- The apps domain setting, the applications certificate and its two routes, the
  per-application label, the `/launch` hand-off, `app.session.start` and `app.session.end`,
  the per-request application log, and the `apps_not_ready` refusal.

**Tests, for the record**
- The relay, the browser orchestration, the connect path and the settings each have unit
  tests; the console's portal, checklist, Watch and recordings paths have theirs. A
  Docker-gated test runs on every change against a real guacd, the real browser image and an
  nginx: guacd's image instructions arrive in the session's socket, the containers sit on the
  networks the design says with the hardening in place, and the end of the session removes
  all three. That test found three bugs before the first operator did.

## Upgrading from 1.6.0

**Back up first** (`zanskar backup`). Install the new package, or set `ZANSKAR_VERSION=1.7.0`,
and restart. Migration 0032 drops the `app_sessions` table, the per-application label, the
`apps.domain` setting and the applications certificate on both engines; applications
enrolled under 1.5 or 1.6 keep their upstream.

**What an operator must do for applications to open**
- **A container runtime the service can reach**, the same requirement as database access:
  `systemctl edit zanskar` with `SupplementaryGroups=docker`, or `ZANSKAR_DOCKER_PATH=podman`.
  Applications are not available inside the Compose stack or on Kubernetes, where the
  gateway container has no runtime.
- **guacd on the runtime's default bridge.** The install guide's `docker run` already puts
  it there. The AWS reference install now runs `docker network connect bridge guacd`; an
  install that started guacd on a named network must do the same.
- **The browser image.** The default is `ghcr.io/albatroxxx/zanskar-browser:1.7.0`, pulled
  on the first session. A host without registry access sets `ZANSKAR_BROWSER_IMAGE` to a
  mirror or a local build of `deploy/browser`.
- **Remove what the proxy needed.** `ZANSKAR_APPS_DOMAIN` in the environment file is no
  longer read; the wildcard DNS record and the certificate for the old apps domain can go.

**Not in this version**: resizing after the session opens (the screen is the size the
window had when it was opened), sound, file upload into the application, credential
autofill from the vault.

**API changes**: `POST /connect` with protocol `http` issues a desktop ticket for
`/ws/desktop`, with no credential; it answers `501 protocol_unavailable` until guacd and the
images are set, and `/ws/desktop` answers `503 too_many_sessions` over the cap.
`GET /me/targets` lists an application without `label` and `url`. `GET
/admin/applications/readiness` keeps its shape with the keys `guacd`, `runtime` and `image`.
`GET /me/applications/launch`, `PUT` and `DELETE /admin/tls/apps` are gone; `GET /admin/tls`
no longer carries the `apps*` fields; a target has no `app_label`. The `http` protocol stays
in policies, sessions and audit.
