# Zanskar 1.4.0

A security release. In October the whole gateway was read end to end, by tools and by six
reviewers with a brief each, and every finding was fixed: eight serious ones in the session
path and at sign-in, thirty-three of medium weight, seventeen smaller ones, thirty-one plain
bugs, and the dead and duplicated code that let some of them hide. The published 1.3.0 image
also carries three Go advisories (denial of service in HTTP/2, HTTP range requests and TLS);
this release is built with the fixed Go 1.27.2.

Nothing here needs a new setting to keep working. Read **Upgrading from 1.3.0** below before
you install: one migration rewrites data, and a few behaviours changed on purpose.

## What was wrong and is now fixed

**Sessions obey the policy that admitted them**
- A connect ticket for a desktop or PowerShell session could be presented to the terminal
  endpoint and open an SSH shell on a Windows host that also runs OpenSSH, with the RDP
  credential, when the policy allowed only RDP. Every session endpoint now checks that the
  ticket was issued for its protocol.
- A ticket is now redeemed only by the sign-in that asked for it, within its thirty seconds,
  and the policies and the account's roles are checked again at that moment. A leaked ticket
  is useless without the cookie, signing out ends it, and an account made review-only in
  between starts nothing.
- A clipboard-off policy used to drop only the first frame of a clipboard transfer; the text
  itself still reached the browser. The desktop bridge now drops the whole transfer, and guacd
  is told to disable copy and paste at the source.
- The browser's clipboard goes to a desktop only when you press Ctrl+V or Cmd+V in it. Before,
  it was read every time the window regained focus, so a password copied for something else
  landed on the remote machine's clipboard.
- An approval-gated policy no longer lends its clipboard, file, MFA and timeout settings to a
  session that a standing policy admitted. A selector tag with an empty value no longer
  matches every target that lacks the tag.
- Only keystrokes keep a session from going idle; window resizes and keep-alive frames do not.
  A session window written as `00:00` to `00:00` means all day rather than never.

**Taking access away ends live sessions**
- Disabling or locking an account, changing its roles, revoking its sign-ins, removing it from
  a group, and deleting or narrowing a policy now end the SSH, desktop, PowerShell and
  database sessions that access allowed. Before, an open session ran until its idle timeout,
  up to twenty-four hours, and the only way to stop it was to find and end each one by hand.
- The person sees why: the session closes with its reason (*policy revoked*, *ended by an
  administrator*, *gateway restarting*), not as a lost connection, and the console no longer
  offers to switch to another autoscaling instance when the gateway itself ended the session.
- Live shadowing of SSH and PowerShell sessions works. The auditor's watch page received the
  start and the end of a session and nothing in between; the bridge was never connected to it.

**Sign-in**
- After single sign-on, the gateway could be made to redirect to another site through a
  crafted return path (a tab character passed the check and browsers strip it). The return
  path must now be a path on this site, and the sign-in page no longer shows text from the
  address bar, so a link cannot make the real page carry a scam message.
- Wrong authenticator codes now count against the account like wrong passwords: five lock it
  for fifteen minutes. Before, a correct password reset the count, so codes could be guessed
  without limit. A wrong *current password* on the change-password form counts the same way,
  and adding an authenticator from a signed-in session asks for the password.
- A temporary lock from five wrong passwords no longer throws that user out of the console.
  Anyone who knew a username could do that every fifteen minutes. An account an administrator
  disables or locks is still refused on its next request.
- Completing a sign-in issues a new session token, so a cookie planted before sign-in never
  becomes a signed-in one. Changing your own password ends your other sessions.
- The number of password checks running at once is capped (each costs 64 MiB), rate limiting
  groups IPv6 addresses by /64, and a flood of refused sign-ins is audited once, not per
  attempt, so it cannot grow the hash-chained log without bound.
- Accounts created ahead of time for a directory or single sign-on user can sign in: the
  gateway adopts a local account with the same username and no password, and records the link.
  Before, `auto_provision: false` could never admit anyone.
- An account provisioned at first sign-in is recorded as `user.create` with its roles. Group
  memberships a sign-in changes are recorded, and removal from a group ends the sessions that
  group allowed. Identity provider settings that affect access are recorded before and after
  each change.
- LDAP group mappings written as a distinguished name are compared exactly, so a same-named
  group in another OU no longer matches. The console form accepts DNs and the guide recommends
  them.
- Allowed email domains apply only to an address the provider marked verified. Entra ID never
  sends that mark, so a provider setting, *trust email*, accepts its addresses; the console
  says when to tick it.
- Behind a proxy that terminates TLS, set `ZANSKAR_PUBLIC_URL` to the https address people use,
  and single sign-on builds the redirect URI the provider has registered. It could not before,
  which made OIDC unusable in that deployment.

**Database sessions**
- The client container's network is internal: it reaches the relay and nothing else. Before,
  it had the gateway host's full network, and the official `psql` and `mysql` images carry
  shell escapes. The session user also no longer gets pgbouncer's admin console, which showed
  the upstream host and user and could pause the pool.
- At most twenty database sessions run at once (`ZANSKAR_DATABASE_MAX_SESSIONS`; 0 lifts the
  cap), and a reaper removes client containers a crashed gateway left behind.
- The `docker` commands the gateway runs inherit none of its secrets. The gateway drops its
  master key, database address and webhook secret from its own environment once read; keep
  the key in `ZANSKAR_MASTER_KEY_FILE` and it never appears in `/proc/<pid>/environ` either.

**Audit**
- A client that disconnected right after a change could leave it unaudited: the audit write ran
  under the request's context and was cancelled with it. Audit writes now finish regardless.
- Audit anchors, as ADR 0008 promised. The gateway signs the head of the log at start, every
  hour, and on `zanskar audit anchor`, under a key derived from the master key, and logs each
  anchor as a line to ship off the host. `zanskar audit verify` and the Events page check the
  anchors, the id sequence and any anchor you pass in, so deleting the newest events is noticed;
  before, only an edit in the middle of the chain was.
- Every file transfer attempt is audited with its outcome; a failed upload went unrecorded and
  an interrupted download was recorded as a success. A recording that could not be saved is
  audited as `recording.lost` and never shown as a finished recording that then fails to play.
- Host-key and certificate mismatches on autoscaling instances are audited when first seen,
  not on every poll (about 2,880 events a day per instance before). The SIEM webhook follows
  no redirect, so a signed batch is never re-sent elsewhere or over plain http.
- Audit action names are constants, checked against the console's labels by a test, so a new
  action cannot ship without a label.

**Targets and certificates**
- A probe never replaces a pinned RDP or WinRM certificate. A different certificate is held as
  pending, audited, and pinned only when an administrator accepts it on the target's page. A
  certificate mismatch at RDP connect time is audited like SSH and WinRM mismatches are.
- Addresses that must never be targets are refused when a target is saved and again when a
  session dials it, for every protocol, database targets included: loopback and link-local
  addresses, the gateway's own address, and the metadata services of AWS (IPv4 and IPv6), EKS
  Pod Identity, Alibaba Cloud, Azure and Oracle Cloud.
- Approval-gated access to an autoscaling group can be requested from the user portal. The
  group showed as allowed, connecting was refused, and there was no way to ask.
- The name of a cloud-side autoscaling group is quoted in the paste-ready IAM script and the
  CloudFormation template, so a quote or a line break in it cannot change what the script does.
  A group stores its values trimmed, GovCloud and China role ARNs are accepted, *Test access*
  assumes the role afresh instead of reusing credentials cached for fifteen minutes, a failing
  group backs off exponentially, and groups sync side by side.
- An uploaded TLS certificate that cannot serve (a clock behind its start date at boot, say) is
  kept, not deleted, and the Settings card says why it is not in use. Before, the certificate
  and its key were removed and, with HSTS, the console was unreachable. A failed regeneration
  leaves the old self-signed certificate serving, and that certificate renews while the gateway
  runs, within thirty days of its end.

**Operations**
- `zanskar init --force` on an install that keeps its key in `ZANSKAR_MASTER_KEY_FILE` keeps it
  there. Before, it minted a new inline key and the service could not open anything.
- `zanskar restore` run as root gives the database and recordings to the owner of the files
  they replace, so the service's own user can open them.
- `zanskar key rotate-master` writes the new key only where the service reads the old one; any
  other file is refused, and it re-signs the audit anchors under the new key. Restart the
  gateway straight after, as the command says: until then the running gateway holds the old
  key, and rather than write an anchor nothing could verify later, it writes none and logs why.
  A running gateway picks up a key version added by a rotation elsewhere on first use, and
  `key status` counts every sealed column.
- Every offline command (`admin reset-mfa`, `audit`, `key`) refuses a database with migrations
  pending, as `admin create` already did.
- An environment value is never silently ignored. Yes/no variables take `true`, `1`, `yes`, `on`
  and their opposites; anything else refuses the start and names the variable. A setting's
  value that fails its check (`ZANSKAR_GUACD_ADDR` without a port, say) refuses the start
  instead of switching desktops off with no word, and settings that do nothing in the current
  configuration are named in the log at start. `ZANSKAR_ADMIN_LISTEN_ADDR` is refused: it was
  shown on the boot panel but never bound a listener, so it promised an isolation it did not
  give (ADR 0010 is amended).
- `zanskar healthcheck` asks the gateway's own readiness endpoint, for the container image,
  which has no shell. The compose stack has health checks on every service, Caddy starts once
  the gateway is healthy, Caddy and guacd are pinned by digest and run with capabilities
  dropped. A Helm upgrade stops the old gateway before it starts the new one.
- The release pipeline builds the console in a job that holds no write token, so no npm build
  code runs where it could push the image or sign the release.
- Timestamps compare correctly on SQLite. Stored times had their trailing zeros trimmed, and
  SQLite compares text, so inside one second the order was wrong: audit filters were off by up
  to a second, a grant could read as active just after it ended, and sessions listed out of
  order. Every timestamp is now written in one fixed form (see Upgrading).

**The API**
- Every error carries its `request_id`, in one envelope, as the documentation always said; the
  console shows it on a server error as *reference …*. The same situation now gets the same
  code everywhere (a duplicate name is `conflict`; a missing referenced record is
  `bad_request`), and constraint errors are recognised by the driver's code rather than its
  message text, so a driver release cannot turn them into internal errors.
- Deleting an account with sessions on record answers `409 has_history` and touches nothing.
  Before, it revoked the sign-ins and ended the sessions and then failed with 500.
- `/api/v1/version` needs a session. Updating a user without `email` keeps the stored email.
  The specification's error codes, probe failures (502), session end reasons and the
  autoscaling group credential choice match the server.

**The console**
- The sign-in page downloads only itself: the admin console and the recording player load when
  they are opened (the first download is half the size).
- Tab stays inside an open dialog. The recording player's command list and the tab bars work
  from the keyboard and with a screen reader. Text on the accent colour is readable in dark mode.
- A deep link survives signing in, including from single sign-on. The console keeps a session
  through a gateway that does not answer (a restart) and signs out only on a 401. A list that
  could not be read says so instead of looking empty. A double-click on Disable no longer turns
  the target back on, and the audit log's *Load more* no longer adds rows from a filter that
  changed while it was loading.
- The ended-session dialog is the same on the terminal and the desktop, with the reason in
  words; the desktop's clock stops when the session ends. The autoscaling group form picks
  credentials the way the drawer does, including the user's own login.

**Dependencies**
- Go 1.27.2 (fixes CVE-2026-78667, CVE-2026-78669 and CVE-2026-97031, all denial of service),
  `golang.org/x/net` 0.60.0, the AWS SDK, go-ldap, and the console's build tools.

## Upgrading from 1.3.0

**Back up first**: `zanskar backup`, or your database's own tool. Three migrations are
pending after the upgrade. Two add tables and columns (audit anchors, pending target
certificates). The third, on SQLite only, rewrites every stored timestamp into one fixed form,
in one transaction: a million audit events (a 350 MB database) took seven seconds on a laptop SSD, and it needs free disk space of about the database's size while it runs. On PostgreSQL it changes nothing. Running it twice changes
nothing, and an interrupted run leaves the database as it was.

Install the new package, or set `ZANSKAR_VERSION=1.4.0`, and restart. `serve` refuses to start
while a migration is pending; the packaged service and the compose stack run `zanskar migrate`
before the gateway starts, so a restart is enough there. Run it yourself only where you start
`serve` some other way.

**Check your environment file before restarting.** The gateway now refuses to start on:
- `ZANSKAR_ADMIN_LISTEN_ADDR` set to anything. Remove it; the admin console was always on the
  main listener.
- A yes/no variable (`ZANSKAR_TRUST_PROXY_TLS`, `ZANSKAR_ALLOW_PLAIN_HTTP`) with a value other
  than `true`/`false`, `1`/`0`, `yes`/`no` or `on`/`off`. Before, anything but `true` read as
  false. A deployment that set `ZANSKAR_ALLOW_PLAIN_HTTP=1` or `=yes` was running with it off
  and will now run with it on; set it to `false` if that is not what you want.
- A setting given in the environment whose value fails its check: `ZANSKAR_GUACD_ADDR` without
  a port, `ZANSKAR_REQUIRE_MFA` that is not a yes/no word, or `ZANSKAR_DBPROXY_IMAGE` that is
  not an image reference. The message names the variable.

A relay image saved in the console's Settings that is not an image reference (a mirror with an
upper-case name, say) is no longer used: the gateway names it in the log at start and the
environment value or the default applies until you set it again.

**Behaviour that changed on purpose**
- Live sessions end when access is taken away (see above). An administrator who expects a
  disabled user's session to keep running until its timeout will find it ended.
- Wrong authenticator codes lock the account after five, like wrong passwords.
- Changing your own password ends your other sessions.
- Pressing Ctrl+V or Cmd+V in a desktop session pastes the browser's clipboard; window focus
  no longer does.
- A probe that finds a different RDP or WinRM certificate no longer pins it; accept it on the
  target's page. An existing pin is kept.
- A database target, or any target with a loopback, link-local, gateway or cloud metadata
  address, is refused at save and at connect.
- At most twenty database sessions run at once; raise or lift the cap with
  `ZANSKAR_DATABASE_MAX_SESSIONS`.
- The audit log writes one anchor an hour. Ship the gateway's log off the host so the anchor
  lines live outside the database; the [deploy guide](../deploy.md#audit-anchors) explains
  what each check catches.

**New settings, all optional**
- `ZANSKAR_PUBLIC_URL`: the https address people use, needed for single sign-on behind a proxy
  that terminates TLS.
- `ZANSKAR_DATABASE_MAX_SESSIONS`: the cap above (default 20, 0 for none).
- *Trust email* on an identity provider, for providers that never mark an address verified.

**Compose users**: the new `deploy/docker-compose.yml` needs Docker Compose 2.20 or newer, and
the gateway's health check uses `zanskar healthcheck`, which the 1.3.0 image does not have;
with the new file and the old image the gateway shows unhealthy and Caddy starts anyway after
a minute. Debian 12's own `docker-compose` package is too old; install Docker's.

**API changes**: every error body carries `request_id`. New: `POST /targets/{id}/certificate/trust`,
`asg_id` on `POST /me/access-requests`, `trust_email` on identity providers, `409 has_history`
on `DELETE /users/{id}`, `cli_locked` (429) distinct from `cli_code_required` (403),
`policy_revoked` and `gateway_restart` end reasons, `recording.lost`, `target.tls.changed`,
`target.tls.trust`, `user.link` and `user.groups.sync` audit actions. `/api/v1/version` needs a
session. A desktop session closed by the gateway carries WebSocket status 523 with its reason;
519 means only a lost target.
