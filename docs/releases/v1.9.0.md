# Zanskar 1.9.0

The console after a walk through it on a live gateway. Host actions and updates show their
progress and how they ended; install settings change from the console through a root
helper that rolls back a change the gateway does not come back from; the gateway gets its
own Let's Encrypt certificate in managed mode; deleting a host takes it out of its
policies; every time follows one time zone; the dashboard reads in percentages; the policy
list and editor handle dozens of targets; and the browser image is lighter, with old images
removed after an upgrade. Built with Go 1.27.3.

## What changed

- **Host actions show progress.** Restart gateway, Reboot host, Stop host and Install
  follow the action to its end: waiting for live sessions (how many, until when), the
  installer's own words, restarting, and back, with a green tick ("Updated to 1.9.0",
  "Host rebooted") or the reason it failed. Success is judged by the gateway's answers: a
  fresh process, on the version asked for. The drain can be cancelled from the same view.
- **The gear and the bell drop from their buttons**, as cloud consoles' Actions menus do.
  An action the host cannot take is greyed with one line of why ("Needs a systemd host.").
- **A theme menu** beside the bell: System, Light or Dark, kept per browser and applied
  before the first paint. The corner icons are 10% smaller. The command line's header is
  glyphs with their words on hover; its code step is one line.
- **The command line maximises**: a Maximise button gives it the whole window and Restore
  brings back its height; the header itself can be dragged, and pulled to the top it
  maximises. A double click on the header does either; the choice is kept per browser.
- **Install settings from the console.** On a package install, Settings, Set at install has
  Edit on the public URL, TLS hosts, issuer, log format, the Apps and Database session caps
  and the AWS gateway principal, and a switch between the managed and proxy TLS presets.
  The gateway never writes its environment file: it asks, after a fresh authenticator code
  and a drain, and `zanskar-config.service` applies the change as root, checks that the
  gateway would start with the new file, keeps the old one as `env.previous`, restarts, and
  puts the old file back if the gateway does not answer within 60 seconds. Everything else
  (database, master key, container runtime, listen address outside the presets, plain
  HTTP, proxy trust, TLS file paths) stays install-only. `zanskar config check --env FILE`
  says whether the gateway would start with a file. ([ADR 0020](../adr/0020-runtime-settings-console-overrides-environment.md), amended.)
- **Let's Encrypt in managed mode.** Settings, Let's Encrypt: on, an account email, and an
  ACME directory (Let's Encrypt by default, or a private ACME CA). The gateway orders a
  certificate for the public URL's host and the DNS names among the TLS hosts, never for a
  name a stranger sends, answers the CA on its TLS and :80 listeners, renews on its own, and
  keeps the account and certificates sealed in the database, so a second gateway on it
  reuses them. An uploaded certificate still wins. A CA that is down costs a handshake at
  most 10 seconds before the next certificate serves. ([ADR 0021](../adr/0021-managed-tls-certificate.md), amended.)
- **Deleting a target takes it out of its policies** instead of being refused while any
  policy names it. The delete dialog lists what it reaches (the policies that lose it, a
  grant left naming nothing, live sessions, open access requests) and asks for the name;
  one transaction removes the target from every grant and closes its requests, then its
  sessions end (`target_deleted`). A policy left with no grant stays and grants nobody.
  ([ADR 0036](../adr/0036-access-policy-grants.md), amended.)
- **One time zone.** Settings, Display, Time zone sets the zone of every time in the
  console, all three portals, and of the dashboard's new clock; the default is the gateway
  host's zone. The operating system is not touched.
- **The dashboard reads in percentages**: CPU busy, memory used, and each disk as `df`'s
  Use%, in the warning colour when it is one. A CPU reading after a long gap starts fresh
  instead of averaging the gap.
- **The policy list** sums each policy up ("3 grants · Host 2 · Autoscaling 1") with an
  Access column for the loosest terms (a danger badge on standing access without an
  authenticator) and opens to a table of its grants.
- **The policy editor** has Select all in every pick list, an "All chosen" row that sets one
  protocol on every chosen target, and shows the protocols a target's operating system
  usually serves that its last probe did not find, greyed; one a grant already chooses shows
  in the warning colour.
- **Add host** asks for a hostname or IP address and shows the ports its operating system
  uses, with the rarer ones under More ports. "Recording retention (days)" says its order:
  the target's, then the grant's, then the global.
- **Users and groups**: pick a user's groups as you add the user, and a group's members as
  you create the group (`group_ids` and `user_ids` on the create calls; an unknown or
  provider-synced group, or an unknown user, refuses the whole request).
- **Settings** shows Desktops as an on/off switch, with guacd's address under Advanced, and
  the relay and browser images under Advanced, with a warning on a custom one.
- **A lighter browser image.** Debian 13 with Chromium 156, without the software GL stack,
  Perl or Chromium's Vulkan validation layer, none of which it uses: about a 270 MB download
  and 660 MB on disk, from 340 MB and 900 MB. Releases build its package layer only when
  Debian's packages changed and take it from the previous release otherwise, so most
  upgrades will download a few kilobytes of it. This one is a full download (a new base);
  the saving starts with the release after it.
- **Old images are removed.** On start and every five minutes the gateway removes earlier
  versions' browser and relay images from its host: only images carrying Zanskar's source
  label, never one a container uses, never from a development build. Audited as
  `system.images_remove`. Settings, Updates, Remove old images turns it off.

## Fixed

- The Applications checklist said "cannot use docker: exec: no command" on an install with
  no `ZANSKAR_DOCKER_PATH`, and Add application stayed hidden; sessions worked. The check
  now runs `docker` from the PATH, as sessions do.
- Admin lists (hosts, users, groups, autoscaling groups) loaded their first 500 rows only,
  so the policy editor's pick lists missed the rest. They load every page.
- A failed install (a download that did not verify, a package that would not install) left
  the gateway draining, refusing new sessions, until someone cancelled. It serves again,
  with a failure audit event, when the installer reports a failure or stays silent for 20
  minutes.

## API

- New: `GET /api/v1/targets/{id}/usage` and `GET /api/v1/autoscaling-groups/{id}/usage`
  (what a delete reaches); `POST /api/v1/admin/settings/boot` and
  `GET /api/v1/admin/settings/boot/result` (install settings).
- Changed: `DELETE` of a target or an autoscaling group named by a policy succeeds and
  removes it from the policy, where it answered `409 in_use`. `POST /users` takes
  `group_ids`, `POST /groups` takes `user_ids`. `/auth/me` carries `time_zone`; the system
  status carries `now`. Live sessions of a deleted target end with `target_deleted`.
- New runtime settings: `display.time_zone`, `tls.acme`, `tls.acme_email`,
  `tls.acme_directory`, `updates.remove_old_images`. New audit actions:
  `settings.boot_request`, `settings.boot_apply`, `system.images_remove`.

## Upgrading from 1.8.0

**Free disk space first** if the host runs applications and is short of it: the new browser
image is a full download, and the gateway removes the old ones on its first pass after the
upgrade, but an application opened before that pass pulls the new image beside them.

```
sudo docker image rm ghcr.io/albatroxxx/zanskar-browser:1.8.0 ghcr.io/albatroxxx/zanskar:1.8.0
```

(add any older `1.7.x` tags `sudo docker image ls | grep albatroxxx` lists). Then install the
new package, or set `ZANSKAR_VERSION=1.9.0`, and restart. To spare the first application
session the pull, pull ahead:

```
docker pull ghcr.io/albatroxxx/zanskar-browser:1.9.0
docker pull ghcr.io/albatroxxx/zanskar:1.9.0
```

One migration runs: 0038 creates the `acme_cache` table. 1.8.0 starts on the migrated
database, so a downgrade needs no restore.

The package installs and enables `zanskar-config.path` and `zanskar-config.service`, which
let the console change install settings. A tarball install or the AWS reference install
does not have them; there, Edit asks and nothing applies it, and the gateway serves again
after 10 minutes saying so; [deploy.md](../deploy.md#changing-boot-settings-and-restarting)
says how to add them.

**Moving a Caddy-fronted gateway to Let's Encrypt in the gateway itself**: switch the TLS
mode to managed from the console only after stopping Caddy (`sudo systemctl disable --now
caddy`), since the gateway needs ports 80 and 443. If Caddy still holds them, the gateway
does not come back on the new settings and the helper puts the proxy settings back after
about a minute. Set the public URL first; Let's Encrypt orders for its host.
