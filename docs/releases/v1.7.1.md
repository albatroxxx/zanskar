# Zanskar 1.7.1

A patch for the first application session on a host, and for the gateway card on the admin
dashboard. Nothing changes in what 1.7.0 does once a session is open; this release makes the
opening survive a slow start and a first-time image pull. Built with Go 1.27.3.

## What was wrong

Two things, found the day after 1.7.0 shipped.

- **The console gave up after fifteen seconds.** The browser's tunnel drops a socket that
  stays silent for fifteen seconds. An application session's socket was silent while the
  gateway created the network and started the relay and the browser, which guacd only draws
  afterwards. On a host where that takes longer than fifteen seconds the session ended as
  *target lost* before the first frame, every time. The end-to-end tests did not see it
  because their client has no such timeout.
- **The first session on a host had seconds to pull hundreds of megabytes.** The whole
  set-up ran under one forty-five second deadline, image pulls included. The first
  application session on a host that had never run one pulled the browser image (about
  320 MB) and the relay image inside that budget; on a slow link it failed, and the second
  session worked because the images were there by then. Database sessions had the same
  shape with a thirty-second budget.

## What changed

- While the containers start, the socket hears a keepalive every three seconds, from before
  the first container to guacd's first instruction, so the console's tunnel stays open for as
  long as the start takes.
- The images are checked before any session object is made and, when the host lacks one,
  pulled first under a deadline of their own (ten minutes), for applications (relay and
  browser) and for database sessions (sidecar and client image) alike. A pull that fails says
  which image and which command to run. A user who leaves cancels the pull; the layers
  already fetched stay cached.
- The Applications checklist's *Browser image* line now says whether the image is on the
  host, and gives the `docker pull` to run ahead when it is not.
- The desktop page shows *Connecting* in its bar until the first frame, instead of a black
  pane with no word.

**The gateway card shows CPU use.** The admin dashboard's card showed the load average,
which stands at 0.00 on a lightly used box and is not what an operator asked for, and it read
its numbers once, so they never moved until a reload. The card now shows how busy the
processors were, as a percentage across all of them, with the fifteen-minute load beside it,
and reads the host's numbers again every ten seconds while the page is open. The metrics
route (`GET /admin/system/metrics`) gains a `cpu` object (`percent`, `window_seconds`),
measured between two readings of `/proc/stat`: the first request takes two a moment apart,
later ones measure since the previous request. A host without `/proc/stat` keeps the load
gauge.

**Dependencies.** `golang.org/x/net` moves to v0.62.0, which closes two advisories
(GO-2026-6860, GO-2026-6866) that `govulncheck` lists against the module and that the
gateway's code does not reach.

## Upgrading from 1.7.0

Nothing to configure and no migration. Install the new package, or set
`ZANSKAR_VERSION=1.7.1`, and restart. The default browser image follows the gateway's
version, so the first application session after the upgrade pulls
`ghcr.io/albatroxxx/zanskar-browser:1.7.1`; to spare that user, pull it ahead on the
gateway host:

```
docker pull ghcr.io/albatroxxx/zanskar-browser:1.7.1
docker pull ghcr.io/albatroxxx/zanskar:1.7.1
```

Everything in the **Upgrading from 1.6.0** notes of 1.7.0 still applies if you are coming
from further back.

**For the record**: the fifteen-second behaviour is covered on both sides, by a gateway test
that asserts the keepalive reaches the socket before the tunnel id, and by a console test that
drives the real tunnel library with a stand-in socket and fake clocks: nops before the id keep
it open, the id is still taken after them, and silence after that still times out. It was not
exercised against the whole console page, which has no desktop end-to-end test yet. The pull
path was run end to end against a real guacd with the published browser image removed from the
host first.
