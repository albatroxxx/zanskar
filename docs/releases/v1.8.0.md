# Zanskar 1.8.0

Access policies, redesigned ([ADR 0036](../adr/0036-access-policy-grants.md)). A policy now
says who it is for, any number of groups and users, and holds grants; each grant picks a
type of target, then the targets with a protocol each or tags, then its own conditions.
Approval, an authenticator, clipboard, file transfer, limits, windows, recordings and how
a person signs in are set per grant, so one policy can give the same team standing SSH to
staging and approval-only RDP to production. Every stored policy is converted on upgrade,
with the same access. Built with Go 1.27.3.

## Breaking: the policy API

`/api/v1/access-policies` keeps its address and changes shape: `subjects` and `grants`
replace `group_id`, `user_id`, `target_selector`, `protocols`, `rules` and the conditions at
the policy level. A body in the old shape is refused with `400 legacy_policy_shape`, naming
the field, rather than read in part: a client that wrote it would otherwise drop every
other subject and grant in silence. The console, the console's command line and the
scripts in `hack/` speak the new shape. A script of your own that writes policies needs
the change; see the API reference.

## What changed

- **Who.** Many groups and users per policy, picked from searchable lists. Deleting a group
  or a user takes it out of its policies, which stay; a policy left with no one grants
  nobody and is marked in the list. (Before, deleting a group deleted its policies.)
- **Grants.** The type comes first: host, database, application or autoscaling group. A
  grant lists only targets of that type and offers only the protocols that type serves, so
  SSH can no longer be granted on a database. Each chosen target shows the protocols it
  serves (what a probe found, else what its operating system usually serves). Tags are Key
  and Value rows; every key must match, and a key given twice matches any of its values.
- **Conditions per grant**: standing or approval; sign in with the target's credential or
  the person's own login; authenticator; clipboard; file transfer; idle and maximum; days to
  keep recordings; time windows.
- **Overlap.** Standing access wins over approval; of the grants that let a person in, each
  limit is the strictest: the shortest idle timeout and maximum, clipboard and file transfer
  only if every grant allows them, an authenticator if any grant requires one, the longest
  retention. Before, the policy with the shortest idle timeout set every term, so a stricter
  overlapping policy could lose its authenticator or clipboard setting.
- **Live sessions** are checked again whenever a policy, a group's members or a group
  changes, against everything the person may do now: a session ends when a fresh connect
  would be refused, or when its clipboard or file transfer would now be off. A shorter
  limit or a window shutting does not end a session already running. Another policy that
  still covers it now keeps it open.
- **Just-in-time.** A request is eligible under the approval grants that cover it; the cap is
  the shortest of their maximums, no longer the first policy's by name; the request records
  the grant (`grant_id`).
- **Signing in as yourself.** Where a grant says *their own login*, the access portal offers
  *as me* beside the protocol; where every grant that admits says so, connect asks for the
  person's login whatever the target's credential slot holds.
- **The editor** is a page: Policy, Who, Grants, each grant a card that reads as one line
  when closed, with Duplicate and *Add grant, same conditions*. The list shows one line per
  grant.
- **The access portal** lists a target under the protocols its type serves only.

## Upgrading from 1.7.2

Three migrations run. The package's upgrade and the systemd unit (`ExecStartPre`) run
`zanskar migrate` for you; anywhere else, run it before `zanskar serve`, which refuses to
start while any is pending. 0035 creates the subjects table and copies each
policy's group or user into it; 0036 converts every policy into grants; 0037 drops the old
columns, and refuses to if any policy was not converted.

The conversion keeps access exactly: each policy grants what it granted, under the
conditions it had. A tag rule reached every type before, so it becomes a grant for each
type its protocols reach: a tag rule granting SSH becomes a host grant and an autoscaling
grant. Delete the half you never meant. Targets that no longer exist, or that serve none of
the policy's protocols, are left out and named in the log. Where several policies admit the
same session, its terms can now be stricter than before (above); never looser.

Back up first (`zanskar backup`); a downgrade to 1.7.x needs the backup, since 1.7.x cannot
read the new shape.

**For the record**: the conversion was checked against a frozen copy of the 1.7 evaluator:
for every legacy policy shape, every target type, every protocol it can serve and instants
inside and outside time windows, each policy converted alone grants exactly what it did
under exactly its terms; all together grant the same access with each term at least as
strict; the same holds after a real migration on SQLite and PostgreSQL; and a fuzz of
177,000 random policy sets found no difference.
