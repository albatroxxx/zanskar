# Zanskar 1.10.0

Applications open in a full browser, with developer tools for the people a grant allows;
the dashboard says whether access is safe, whether the evidence is whole, what access is in
flight and how full the gateway is, with a week of history; Users and groups say where each
account comes from; and four fixes from the live 1.9.0 console, two of them in the
identity-provider sync. Built with Go 1.27.3.

## What changed

- **An application opens in a full browser** ([ADR 0037](../adr/0037-application-modes-proxied-and-isolated.md),
  phase 1). Kiosk mode hid the address bar, tabs and developer tools, so an engineer could
  not see where a page was or troubleshoot it. The isolated browser is now a full Chromium
  window: its own address bar, tabs, Back, Forward, Reload and Home. Every new tab and Home
  open the application, and closing the last window opens it again; the session ends from
  the console. The console's own Back/Forward/Reload/Home bar, added for kiosk mode in
  1.7.2, is gone. Confinement is unchanged in effect: the application's origin and nothing
  else, with `chrome://`, `chrome-untrusted://`, `file://`, `javascript:` and `view-source:`
  blocked by name besides; no downloads, printing, extensions, sign-in, sync or autofill.
  A session takes about a tenth less memory (Chromium's low-end-device mode).
- **Developer tools by grant.** An application grant has a new condition, *Developer tools*,
  off by default (`allow_devtools`). Granted, the session's browser opens its developer
  tools; otherwise they are off and `devtools://` is blocked. Where several grants admit,
  each must allow them, and withdrawing them ends a running session at the next re-check,
  as the clipboard does. The tools see the one session they are in, its cookies and
  storage included, so grant them to the people who may change the application's state
  in their own session: a QA or application engineer, not everyone who may use it. The
  policy list, the grants table and the command line name the condition.
- **The dashboard says more**, in four new groups, counts only and each number a link:
  - *Security posture*: grants that admit without approval and ask for no authenticator
    (and the policies holding them, in the danger colour when any), accounts with no
    authenticator yet, accounts that have not signed in for 90 days, and administrators.
  - *Integrity*: the audit chain, checked in the background a minute after start and
    every six hours ("Not checked yet" until then, never "intact"); the day's audit events;
    recordings lost in the last seven days; identity providers listed on a schedule (in
    sync, failing, or holding accounts back); and whether the SIEM export keeps up.
  - *Access in flight*: Pending approvals says how long the oldest request has waited, and
    a Grants active tile counts the just-in-time grants running now and those ending
    within the hour.
  - *Capacity and trends*: the Sessions and Refused connections tiles draw the last seven
    calendar days in the console's time zone, today last; hover a column for its day and
    count. The gateway card shows application and database sessions against their caps,
    warning at four fifths and in danger at the cap, where the next one is refused, and the
    disk Zanskar's container images take.
- **Users and groups say where they come from.** A Source column names the identity
  provider that owns an account or a group (by SCIM, the directory sync or its first
  sign-in), outlined so it never reads as a role; *Zanskar* for one made here; *Single
  sign-on* for an account made here to sign in through a provider and not linked yet.
- **Pick lists set the second name apart**: the display name beside a username, the
  operating system beside a host and the member count beside a group sit in a small box of
  their own, so "ashish.gupta Ashish Gupta" no longer reads as one name. A group's Members
  dialog shows the username first, the same way.
- **An account its identity provider took away is not enabled by hand.** While the provider
  still lists or pushes its people, an account the sync or SCIM disabled because the person
  left it keeps its status: Enable is greyed out and the status says *Keycloak no longer has
  this person*. It is enabled again by itself when the person is back. An account disabled
  by hand stays the administrator's to enable. ([ADR 0035](../adr/0035-identity-provider-owns-the-person.md), amended.)

## Fixed

- **After deleting a host, database or application from its detail dialog, no page
  scrolled** until a reload, so the policy editor's grants could not be reached. Two
  dialogs closing together put back the page lock of the one under them.
- **Sign-in through a provider failed with "Invalid parameter: redirect_uri"** on a gateway
  behind a TLS proxy (`ZANSKAR_TRUST_PROXY_TLS`) with no public URL: the redirect address
  was derived as `http://`. With the proxy setting on, derived OIDC and SCIM addresses are
  `https://`. A set public URL still wins.
- **Disable on a held removal did nothing when the directory listed no one.** A realm whose
  only person was deleted lists no one; the scheduled sync holds that back on purpose, and
  Sync now offers to apply it, but the applied run held it back again. It now disables the
  account and ends its sessions. The last active administrator is still never disabled.
  The dialog reads in the singular for one account.

## API

- New: `allow_devtools` on application grants (refused on any other kind);
  `provider_sign_in` on users; `posture`, `integrity`, `in_flight` and `trends` on
  `GET /api/v1/admin/overview`; `application_sessions`, `session_caps` and `images_bytes` on
  `GET /api/v1/admin/system/metrics`.
- Changed: `PUT /api/v1/users/{id}` answers `409 left_provider` to a change of status on an
  account its provider took away (`directory_removed_at` set) while that provider still
  lists or pushes its people; a name or email edit still applies. A forced sync
  (`apply_removals`) applies removals held back by an empty listing. Behind a TLS proxy,
  derived OIDC redirect and SCIM `Location` addresses are `https`.

## Upgrading from 1.9.0

Install the new package, or set `ZANSKAR_VERSION=1.10.0`, and restart.

One migration runs: 0039 adds the two indexes the dashboard's per-day counts need
(`access_sessions.started_at` and `audit_events(action, outcome, ts)`; without them the
overview took 2.5 seconds at 500,000 audit events on SQLite, with them 85 ms). It takes
seconds even on a large audit log. 1.9.0 starts on the migrated database, so a downgrade
needs no restore.

The browser image changes only in its start script, and its package layer is 1.9.0's, so
most hosts download a few kilobytes of it; the gateway removes the 1.9.0 images on its first
pass after the upgrade. To spare the first application session the pull, pull ahead:

```
docker pull ghcr.io/albatroxxx/zanskar-browser:1.10.0
docker pull ghcr.io/albatroxxx/zanskar:1.10.0
```

A gateway set to a custom browser image (Settings, Advanced) needs one built from this
release's `deploy/browser`: an older start script ignores the developer-tools grant and
opens in kiosk mode.
