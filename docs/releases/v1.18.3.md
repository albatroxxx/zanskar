# Zanskar 1.18.3

An account can be deleted whatever it did. Until now the console refused to delete anyone who had
ever opened a session or watched a recording ("disable it instead"), which in practice meant
nobody could be deleted. The history no longer needs the account to stay: a session and a
recording view keep who the person was, the way the audit log always has. Nothing widens what a
session can reach. Built with Go 1.27.3.

## Changed

- **Deleting a user keeps their history** (ADR 0046). The sessions they opened, the recordings
  they watched and the audit events they acted in stay in the record. A session or a recording
  view now carries the person's id, username and display name as they were when it was written.
  While the account exists the console shows its current name; once it is gone it shows the name
  the record kept, marked *(deleted)*.
- **The audit log names a deleted person.** Events they acted in show their username, marked
  *(deleted)*, taken from the `user.delete` event or, for an account deleted before that event
  carried a name, from the copy on their sessions. The Events filter by actor and the Sessions
  filter by username still find them by the name they had.
- **Delete refuses only what is unsafe**: your own account, and the last active admin. Their
  sign-ins are revoked and their live sessions end first, as before. The `409 has_history`
  answer is gone, and the dialog says their past sessions stay in the record.
- A new account with the same username is a different person: it starts with no history, because
  the record is kept by id.

## For contributors

- `access_sessions` and `recording_views` no longer reference `users`. Migration 0054 drops the
  constraint (a rebuild of both tables on SQLite) and fills the copies from `users`. Starting a
  session or recording a view for an account that does not exist returns `session.ErrUnknownUser`,
  because the database no longer refuses it.
- Redacting a deleted person's name from the record was left out on purpose; it can be added as
  its own action that keeps ids and events and clears names.

## Upgrading from 1.18.2

Install the new package, or set `ZANSKAR_VERSION=1.18.3`, and restart. **Migration 0054 rebuilds two
tables** and runs in moments on a gateway of any usual size; back the database up first, as for any
upgrade with a migration.

**A deleted person's username and display name stay in the sessions, the recording views and
the audit log.** That is the record, not a leak, but it is a change from refusing to delete: it means
deleting an account no longer removes the person's name from the gateway. There is no way to blank
it yet.

In the API, `DELETE /users/{id}` no longer answers `409 has_history`, and a session of a deleted
account carries `user_deleted: true` with the `username` it had.
