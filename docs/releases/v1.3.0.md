# Zanskar 1.3.0

Administrators can now work from a command line inside the console. It runs Zanskar
commands only, opens with a fresh code from your authenticator, and records every line in the
audit log. Authenticator codes also become single-use, and the API documentation now covers
every route the gateway serves.

## Changes

**A command line in the admin console**
- The terminal-window icon at the top right of every admin page, or Ctrl+\`, opens it at the
  bottom of the page. `help` lists the 33 commands: sessions, users, targets, policies, access
  requests, events, logs, settings, autoscaling groups and a restart.
- It is not a shell. Pipes, redirection, variables and anything not in the list are refused,
  no command takes a password or key, and backup, restore, key rotation and audit repair stay
  on the host.
- Only administrators get it. Each command is the same API request a console page makes,
  through the same permission checks, so it can do nothing the console cannot.
- It opens with a code from your authenticator (a recovery code works too), and asks again
  after 15 minutes without a command. Five wrong codes close it for 15 minutes without
  signing you out. A sign-in that proved no code (an identity-provider account, or MFA not
  required) does not open it.
- Commands that end, disable, revoke, change or restart something say what will happen and
  ask you to type a word, usually the name of what you are changing.
- Every line is an audit event, including lines that only read. The Events page shows it as
  *ran "sessions --live" on the command line*, with the API routes it called in the details.
- `ZANSKAR_CONSOLE_CLI=off` in the environment file turns it off. It is deliberately not a
  console setting, so a stolen sign-in cannot turn it back on.
- The reference of every command is in [docs/console-cli.md](../console-cli.md); the design
  is [ADR 0027](../adr/0027-restricted-console-cli.md).

**Each authenticator code works once**
- Before, a code that had been accepted was accepted again for the rest of its window, about
  a minute and a half with the allowance for clock drift. Someone who saw an administrator
  type a code, over a shoulder or on a screen share, and also knew the password, could
  reuse it.
- Now the gateway remembers the last code accepted for each user and refuses that code and
  any earlier one, at sign-in, at enrolment and at the command line. The next code works as
  usual.
- A reused code is recorded as one: *failed the second factor (a code already used)*. Seeing
  that for someone who did not retry may mean someone else read their code.

**The API documentation covers every route**
- Fourteen routes that were missing are documented, among them file transfer, the WinRM,
  database and shadow WebSockets, identity providers on the sign-in page and the audit
  filters. A test now fails if a route is added without documentation.
- Entries that disagreed with the server are corrected: group membership updates,
  autoscaling group responses (and that their list is not paged), ending a session, the audit
  verification result, the session list's filters, the terminal WebSocket's messages and the
  identity provider types. `next_cursor` is absent on the last page, not null.

**Dependencies**
- The session player in the console no longer pulls in a serializer with published
  advisories. The affected code was never part of the built console.

## Upgrading from 1.2.2

Install the new package, or set `ZANSKAR_VERSION=1.3.0`, and restart. Two migrations run at
start and add one column each, to sign-in sessions and to authenticators. No data is
rewritten.

The command line is on for administrators straight away. To keep it off, set
`ZANSKAR_CONSOLE_CLI=off` in `/etc/zanskar/env` before restarting.

**One behaviour change:** an authenticator code works once. A person signing in will not
notice. A script that signs in with a code and then sends the same code again, for example
to confirm enrolment and sign in within the same 30 seconds, must wait for the next code.

**API changes:** new routes under `/api/v1/admin/cli` for the console command line
(administrators only). A reused code is answered like a wrong one: 401 `invalid_code` at
sign-in. No other request or response changed; the documentation corrections describe what
the server already did.
