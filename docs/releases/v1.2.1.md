# Zanskar 1.2.1

A security and supply-chain release on top of 1.2.0. Database connections are verified by
default, the master key can live in a file of its own, and every release file now comes
with a software bill of materials, signed build provenance and a build anyone can repeat.

## Changes

**Database TLS is verified by default** (ADR 0025)
- A new database target checks the database's certificate (`verify-full`) unless you
  choose otherwise, and so needs the CA bundle that signs it. For Amazon RDS that is your
  region's bundle, `https://truststore.pki.rds.amazonaws.com/<region>/<region>-bundle.pem`.
- *Encrypted, not verified* and *Encrypted if offered, not verified* are still there, as an
  explicit choice, and such targets carry a warning in the console. Without verification,
  whoever can intercept the connection can pose as the database and receive its password.
- The console says in words how each database target is protected, instead of showing the
  mode's name.

**The master key can live in its own file** (ADR 0025)
- `ZANSKAR_MASTER_KEY_FILE` names a file holding the key, so it is not in
  `/etc/zanskar/env` beside every other setting. The file must be readable by its owner only,
  or the gateway refuses to start. `docs/deploy.md` has the four commands to move an
  existing key into one.
- `zanskar key rotate-master` rewrites the key file in place, keeping its owner and mode.

**Master key rotation cannot strand the key any more**
- `rotate-master -env-file` used to rewrap the database first and write the file second.
  Run as a user that could not write `/etc/zanskar`, it failed after the rewrap, and with
  `-generate` the new key had been printed nowhere, so every stored secret was lost. It now
  checks that the file can be replaced before touching anything, and if the final write
  still fails it prints the new key rather than dropping it.

**Release files you can check three ways**
- An SPDX software bill of materials beside each `.tar.gz` (`….tar.gz.sbom.json`), listing
  the Go modules compiled in, with versions. The `.deb` and `.rpm` carry the same binary.
- SLSA level 3 build provenance for every file (`zanskar.intoto.jsonl`): which workflow, at
  which commit, built it. Check it with
  [slsa-verifier](https://github.com/slsa-framework/slsa-verifier#installation):

  ```sh
  slsa-verifier verify-artifact zanskar_1.2.1_linux_amd64.deb \
    --provenance-path zanskar.intoto.jsonl \
    --source-uri github.com/albatroxxx/zanskar --source-tag v1.2.1
  ```
- Reproducible builds: the Go toolchain is pinned, and archives and packages no longer
  record who built them, where or when, so rebuilding the tag gives the same bytes.

**Also**
- `klauspost/compress` 1.18.7 (GO-2026-5841; not reachable from Zanskar's code).
- Audit events read *changed their password* rather than *change user alice*.

## Upgrading from 1.2.0

Install the new package, or set `ZANSKAR_VERSION=1.2.1`, and restart. Migration 0025 runs at
start: it writes `prefer`, the value those targets already used, into any database target
stored without a TLS mode, so **no existing connection changes**. Tighten each one to
*Verified* when you have its CA bundle.

**API change:** creating a database target without `tls_mode` now means `verify-full`, which
requires `tls_ca`; a request with neither gets a 400 that says what to send. Pass
`"tls_mode": "require"` (or `"prefer"`) to keep the old behaviour deliberately.

`ZANSKAR_MASTER_KEY` in the environment file keeps working unchanged; the key file is an
option.
