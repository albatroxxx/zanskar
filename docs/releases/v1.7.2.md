# Zanskar 1.7.2

Single sign-on that works with any provider, and the first fixes from walking the live
console end to end. It carries more than a patch usually does: sign-in through an OpenID
Connect provider changes behaviour (read **Before you upgrade**), and two additive
migrations run on start. Built with Go 1.27.3.

## Before you upgrade

- **An OpenID Connect provider now owns the second factor.** Sign-ins through it no longer
  ask for a Zanskar authenticator or its enrolment; the provider's own sign-in is the
  second factor, and a policy's *Require an authenticator* is met by it. **If your provider
  does not enforce MFA, edit it and tick *Also ask for a Zanskar authenticator*.** LDAP and
  Active Directory accounts are unchanged and still enrol a Zanskar authenticator.
- **Signing out ends the provider's session too** (OpenID Connect RP-initiated logout), so
  the next sign-in asks for the provider's password again. Untick *Signing out ends the
  provider session too* for a realm other applications share.
- **Usernames may be email addresses.** Okta and Entra ID send one as the username and were
  refused before; they now sign in with their default claims. A new person from Google gets
  the whole verified address as username, not its local part; accounts already linked keep
  theirs.

## Identity providers, any vendor (ADR 0035)

- **People arrive before their first sign-in.** A provider can push people over **SCIM 2.0**
  (`/api/v1/scim/<provider>`: Okta, Entra ID, OneLogin, JumpCloud, PingOne, Authentik), or
  Zanskar can list them (a Keycloak realm through its admin API, or an LDAP directory) every
  15 minutes and on *Sync now*. Joiners get accounts; leavers are disabled and their live
  sessions end; returners are enabled again. Groups are not provisioned. The SCIM token is
  made in the console, shown once, stored as a hash, and can be replaced or revoked.
- **Ask for the password at every sign-in** sends `prompt=login` and `max_age=0`; a provider
  that ignores both is caught by its `auth_time`, and a stale sign-in is refused.
- *Test connection* says whether the provider offers sign-out at all (Google does not).
- The *Continue with* button is a full-width button; nothing in the console underlines on
  hover.
- **Fixed:** a sign-in that enrolled an authenticator lost its `user.mfa.confirm` audit event.

## The console, walked through

The owner walked the live console and named what was wrong; each is fixed.

- **Every dashboard number opens the list it counted.** *1 refused connection* opens the
  audit log filtered to refused connections in the last day; open sessions, failed sign-ins,
  hosts needing attention, pending requests and grants about to end do the same, in both
  portals. The filters live in the address and show as chips that drop them. The API gains
  what the lists needed: `outcome` on `/audit/events`, `from` on `/sessions`, `attention` on
  `/targets`, and `needing_attention` on the overview, a count of distinct hosts.
- **Tags are a Key box and a Value box**, as cloud consoles draw them, on hosts, databases,
  applications, autoscaling groups and policies; nobody types `key=value` any more. A policy's
  tag rows offer the keys in use and the values seen under each. An identity provider's group
  mapping is rows too: the provider's group in a box, the Zanskar group picked by name rather
  than pasted as an id.
- **The console says less.** Page descriptions, paragraph hints and long confirmations are
  cut to what an operator needs at that moment; what only the console explained moved to the
  guide.
- **Applications have Back, Forward, Reload and Home.** The isolated browser has no address
  bar or buttons, so a link to a site the policy blocks was a dead end. The session's bar now
  carries the four, sent as Chromium's own shortcuts; Home goes to the application's start page.
  The browser image sets that as its home page and opens it in kiosk mode in an ordinary window
  (an `--app` window ignores Home). Proved against a real guacd, the image and an nginx: off a
  blocked page and back, forward, reload and home, each by the request it makes.
- **Applications are added once the gateway can run them.** Until guacd, the container
  runtime and a browser image pass, the Applications page is the checklist with *Check again*
  (which asks afresh); *Add application* appears once they pass. An image the host has not
  pulled yet passes, since the first session pulls it.
- **A user may sign in over SSH with their own private key.** On a target whose slot asks for
  the user's own login, the prompt offers a private key (pasted or read from a file) with its
  passphrase instead of a password. It is unlocked when the ticket is issued, so a wrong
  passphrase is said in the prompt, used for that one session and never stored.
- **Credentials lists the secrets an administrator vaults, nothing else.** The internal
  *user_supplied* row (what a slot points at when the user brings their own login) is no
  longer listed, and the Mode column, the same on every row, goes.
- The Approvals badge counts again as soon as a request is decided, not at the next minute.
- The access portal's tabs each carry a count; *My access* and *My sessions* are *Access* and
  *Sessions*; sign-out sits level with the account name.
- Admin lists say **Manage** where they said *Open*: the button opens the record, not a
  session.
- **Recording retention is a section of Settings**; the old address redirects there.
- The Applications checklist asks the container runtime what a session needs (its version)
  instead of `docker info`, which loads every plugin and failed on hosts where sessions
  worked, and when the runtime is unreachable it says why: not installed, permission denied
  (with the restart the group change needs), not running, or timed out.
- Target lists search as you type, by name or address.
- The access portal lists a database under *database* alone. A tag policy that grants SSH to
  everything tagged `env=prod` also covers the prod database, and the portal offered SSH on it,
  which connect then refused.

## Security

- **HSTS behind a TLS proxy.** The header was sent only when the gateway terminated TLS
  itself, so the recommended setup (a proxy in front, `ZANSKAR_TRUST_PROXY_TLS=true`) never
  sent it. It is sent whenever cookies are marked Secure.

## API changes

All additive except one count:

- `GET /admin/overview`: `targets.active` and the attention counts are over **hosts** now
  (databases and applications have their own tiles); `needing_attention` is new.
- `POST /connect`: `credential` takes `private_key` and `private_key_passphrase` for `ssh`
  (as the API document already said); a key that cannot be read, is too large or whose
  passphrase is wrong is `422 credential_invalid`.
- `GET /admin/applications/readiness?fresh=1` asks the runtime again instead of answering
  from the last fifteen seconds.
- New query parameters as listed above; SCIM routes under `/api/v1/scim/`; provider sync
  routes `GET`/`POST /identity-providers/{id}/sync`; `POST /auth/logout` answers 200 with an
  optional `redirect`.

## Upgrading from 1.7.1

Migrations 0033 (provider sign-out, sync marks) and 0034 (SCIM) run on start; both only add
columns and a table. Install the new package, or set `ZANSKAR_VERSION=1.7.2`, and restart.
Pull the images ahead so the first application session does not wait:

```
docker pull ghcr.io/albatroxxx/zanskar-browser:1.7.2
docker pull ghcr.io/albatroxxx/zanskar:1.7.2
```

Then, per OpenID Connect provider: decide on *Also ask for a Zanskar authenticator* (above).
To have people arrive before their first sign-in, choose *People arrive* in the provider's
form: **pushed** (make a SCIM token and give it the provider) or **listed** (for Keycloak, turn
on the client's service account and give it `realm-management` › `view-users`).

Everything in the **Upgrading from 1.6.0** notes of 1.7.0 still applies if you are coming
from further back.

## What comes next

The access policy form is being redesigned: one policy for many groups and users, targets
picked by kind with a protocol each, and approval, MFA, clipboard, file transfer and how a
person signs in (the target's credential or their own login) per set of targets. It changes the policy API and migrates every stored policy, so it is a minor
release of its own; the design is [ADR 0036](../adr/0036-access-policy-grants.md), proposed.
