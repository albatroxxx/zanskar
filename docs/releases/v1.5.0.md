# Zanskar 1.5.0

A feature release. The console gains a landing dashboard for each role, the gateway can be
restarted, rebooted, stopped and updated from the console itself, and internal web
applications can now be reached through Zanskar the way hosts and databases already are.
Read **Upgrading from 1.4.0** below: one migration adds tables and columns, and applications
need a little setup before the first one can be enrolled.

This is the code that soaked as 1.5.0-rc.1 and rc.2, built with Go 1.27.3 (the same security
rebuild the 1.4.1 patch carries).

## Highlights

**A dashboard for each role (ADR 0029)**
- Signing in lands you on a dashboard, not a list. An administrator lands on `/admin` with the
  fleet at a glance — what waits on a decision, what is live, the inventory of hosts, databases
  and applications, and autoscaling health — each number a link to the page that manages it. An
  auditor lands on `/audit`; a user keeps the Targets page with a small account strip above it.
  The logo returns you to your own dashboard.
- Because each role's dashboard is a path of its own (`/admin`, `/audit`), a reverse proxy or
  WAF in front can scope the admin console to particular networks without touching the rest.
- The gateway card shows the host it runs on: load against its cores, memory, each disk with a
  warning before it fills, the database-session containers running, and whether guacd is
  reachable. The console shows the current reading; a Prometheus exporter and asset monitoring
  are the next step (ADR 0031).

**The console says less, and shows state as glyphs**
- Captions are terse and descriptions are kept to what a reader needs. States that were a line
  of text — *awaiting host key trust*, a TLS mode, a disabled policy — are now a single glyph
  whose words appear the moment you hover and pin open on click; screen readers get the words
  from the control's label. The glyphs are neutral line drawings, no third-party marks.
- OS and database engines show a glyph beside the name rather than instead of it. The sidebar
  shows your username; the full name, email and the rest sit behind it.

**Restart, reboot, stop and update from the console (ADR 0032)**
- A gear in the top-right corner offers *Restart gateway*, *Reboot host* and *Stop host*. Each
  lets live sessions finish for the minutes you choose, asks you to type the gateway's hostname,
  and asks for a fresh authenticator code unless you proved one in the last five minutes. The
  gateway holds no systemd privilege for this: the package ships polkit rules that let the
  service user run exactly `systemctl reboot`, `poweroff` and the restart, and nothing else.
  On Docker and Kubernetes the two host actions are greyed out, with the reason.
- A bell lights when a newer release is published. Once a day, with your consent
  (`updates.check`, on by default), the gateway fetches a small version file from the project
  site — nothing about the gateway is sent — and compares it with the running build. From the
  bell you can install the new version: the gateway drains, then a root-owned path unit the
  package ships fetches the release, verifies its cosign signature and SLSA provenance against
  the release workflow's identity, refuses a downgrade, installs the package and restarts. The
  gateway never downloads or trusts anything itself; it writes one file in its own directory.
- Stopping is deliberate about its cost: nothing in the console can start a stopped machine, so
  bringing it back needs the host or the cloud console.

**Applications: internal web apps through an identity-aware proxy (ADR 0033)**
- An internal web application — a wiki, a dashboard, a build server — can be reached through
  Zanskar instead of a VPN or a bastion. An application is a target with an upstream
  (`http://host:port` or `https://host:port`, verified against the system roots or a CA bundle
  you paste) and a label; policies grant it under a new protocol, `http`, with approvals, time
  windows and limits exactly as for a host.
- Each application is served at its own address, `https://<label>.<apps domain>`, through
  Zanskar's own reverse proxy. The apps domain is a required setting and must differ from the
  console's host, so no application can read the console's cookie or another application's.
  Users open an application in a new tab from the Applications tab of their portal; a browser
  that arrives without a session is sent to the console to sign in and straight back.
- The gateway's cookie and any client-supplied identity header are stripped before the upstream,
  which sees its own host name with the public one in `X-Forwarded-Host`; redirects to the
  upstream's own address are rewritten; WebSockets and HTTP/2 pass through; the upstream comes
  only from the target's configuration, so the proxy is never an open proxy. Each session opens,
  is checked on every request against the sign-in it came from and the policy's limits, and ends
  on a sign-out, a terminate, a policy change or its idle and maximum timeouts, audited as
  `app.session.start` and `app.session.end`. A per-request line goes to the gateway's log —
  method, path, status, size and time, never a query string or a body.
- A restart, reboot or update no longer waits its drain window out for an open application tab:
  application sessions carry nothing in flight, so they end at the restart and reconnect on
  reload, while real sessions still finish in the time you allow.

**Dependencies and build**
- The AWS SDK, the console's build tools and the usual transitive bumps. Built with Go 1.27.3,
  which closes the reachable `crypto/x509` advisory (GO-2026-6809 / CVE-2026-111943) that the
  rc.1 build carried.

## Upgrading from 1.4.0

**Back up first**: `zanskar backup`, or your database's own tool. One migration (0031) is
pending after the upgrade: it widens the protocol checks on access sessions and requests to
allow `http`, adds the application columns and the `app_sessions` table, and lets the
certificate table hold the applications certificate. On SQLite it rebuilds three tables inside
one transaction; on PostgreSQL it alters the constraints. It rewrites no data, running it twice
changes nothing, and an interrupted run leaves the database as it was.

Install the new package, or set `ZANSKAR_VERSION=1.5.0`, and restart. `serve` refuses to
start while a migration is pending; the packaged service and the compose stack run
`zanskar migrate` before the gateway starts, so a restart is enough there.

**Nothing here needs a new setting to keep working.** A gateway that does not use host actions
or applications behaves as before.

**To restart, reboot, stop or update from the console** (ADR 0032): reinstall from the deb or
rpm, which ship the polkit rules and the `zanskar-update.path`/`.service` units and enable the
path unit. A hand-written unit needs those files too; `docs/deploy.md` has them. Installing a
new version from the console also wants `cosign` on the host to verify the release — the package
recommends it; where it is not installed, the bell still lights but the install step says to add
it. Host actions are offered only under systemd.

**To serve applications** (ADR 0033):
- Choose a domain for them that is not the console's own host and not a parent of it
  (`apps.example.com` beside a console at `gateway.example.com`), point wildcard DNS for
  `*.<apps domain>` at the gateway, and set it as the **apps domain** on the Settings page or
  with `ZANSKAR_APPS_DOMAIN`.
- Where the gateway serves TLS, upload a certificate naming `*.<apps domain>` on the Settings
  page (TLS certificate, Applications); the gateway never makes a self-signed one for it. In
  proxy mode the proxy in front terminates it with its own wildcard certificate.
- `ZANSKAR_PUBLIC_URL` (the console's address) is now **required** for applications, so an
  application host can send a browser back to the console to sign in. It was already needed for
  single sign-on behind a TLS-terminating proxy.
- Until the apps domain, the public URL and the certificate are in place, the console names what
  is missing and refuses to enroll an application.

**New settings, all optional unless you use the feature**
- `ZANSKAR_APPS_DOMAIN` / the *Apps domain* setting: the domain applications are served under.
- `updates.check` (on by default): the daily version check that lights the bell.

**API changes**: `http` is a new protocol value on policies, targets and the session model;
`app_upstream` and `app_label` on targets; a new target `kind=application`; `applications` in
the dashboard inventory. New: `GET /me/applications/launch`, `PUT`/`DELETE /admin/tls/apps`,
`GET /admin/overview` and `GET /audit/overview`, the system host-action, metrics and update
routes under `/admin/system/*`, and `POST /auth/mfa/step-up`. The `TLSStatus` body gains the
applications certificate, the apps domain and whether applications can be served. `app.session.start`
and `app.session.end` audit actions; `system.reboot`, `system.poweroff` and `system.update`.
